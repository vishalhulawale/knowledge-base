01
Architecture & Internals
How PostgreSQL works under the hood — processes, memory, storage

Process Model

PostgreSQL uses a multi-process model (not multi-threaded). Each client connection spawns a dedicated backend process. The postmaster is the main daemon that manages lifecycle.

🏠 Postmaster

The parent process. Listens for connections, forks backend processes, manages shared memory init.

⚙️ Backend Process

One per client. Executes queries, holds locks, manages its own portal and memory context.

♻️ Background Workers

Autovacuum, WAL writer, checkpointer, bgwriter, stats collector, logical replication workers.

📝 WAL Writer

Flushes WAL (Write-Ahead Log) buffers to disk. Critical for durability — data is written to WAL before heap.

Memory Architecture

AreaParameterPurpose
Shared Buffersshared_buffersCache for data pages. Start at 25% of RAM.
WAL Bufferswal_buffersIn-memory WAL before fsync. Usually 16MB.
Work Memwork_memPer sort/hash operation. Multiply by concurrent queries!
Maintenance Work Memmaintenance_work_memFor VACUUM, CREATE INDEX. Can be much larger than work_mem.
Effective Cache Sizeeffective_cache_sizePlanner hint — total OS + PG cache. ~75% of RAM.

Storage Layout

Every table and index is stored as a set of 8 KB pages (blocks). Each page has a header, item pointers (line pointers), and tuple data.

SQLInspect page internals
-- Install pageinspect extension
CREATE EXTENSION pageinspect;

-- View raw page header
SELECT * FROM page_header(get_raw_page('orders', 0));

-- View heap tuples on page 0
SELECT t_ctid, t_infomask, t_data
FROM heap_page_items(get_raw_page('orders', 0));

-- MVCC: each row has xmin/xmax to track visibility
SELECT xmin, xmax, ctid, * FROM orders LIMIT 5;

MVCC — Multi-Version Concurrency Control

PostgreSQL never overwrites rows in place. Each UPDATE inserts a new version and marks the old one with xmax. Dead tuples accumulate and are cleaned by VACUUM.

💡

MVCC means readers never block writers and writers never block readers — the foundation of Postgres concurrency.

SQLMVCC visibility
-- Check transaction ID age — important for wraparound prevention
SELECT datname, age(datfrozenxid) AS xid_age
FROM pg_database
ORDER BY xid_age DESC;

-- Tables with many dead tuples (need VACUUM)
SELECT relname, n_dead_tup, n_live_tup,
       round(n_dead_tup::numeric/nullif(n_live_tup+n_dead_tup,0)*100,2) AS dead_pct
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;

Table Creation & Constraints

SQLProduction-grade table design
CREATE TABLE users (
  id          bigint      GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email       text        NOT NULL UNIQUE,
  username    text        NOT NULL
              CHECK (length(username) BETWEEN 3 AND 50),
  status      order_status NOT NULL DEFAULT 'pending',
  metadata    jsonb       NOT NULL DEFAULT '{}',
  created_at  timestamptz NOT NULL DEFAULT now(),
  updated_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE orders (
  id          bigint      GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id     bigint      NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  total       numeric(12,2) NOT NULL CHECK (total >= 0),
  created_at  timestamptz NOT NULL DEFAULT now()
);

-- Partial unique index (unique email per active users only)
CREATE UNIQUE INDEX users_email_active_uidx
  ON users(email) WHERE status != 'deleted';

-- Generated column (computed, stored)
ALTER TABLE users ADD COLUMN
  email_domain text GENERATED ALWAYS AS (
    split_part(email, '@', 2)
  ) STORED;

ALTER TABLE — Zero-Downtime Patterns

⚠️

Many ALTER TABLE operations take an ACCESS EXCLUSIVE lock. On large tables, use pg_repack, concurrent index builds, and careful column additions.

SQLSafe schema migrations
-- Safe: add nullable column (no default = instant)
ALTER TABLE orders ADD COLUMN notes text;

-- Safe in PG11+: add column with default (no rewrite!)
ALTER TABLE orders ADD COLUMN priority int NOT NULL DEFAULT 0;

-- Safe: build index without blocking reads/writes
CREATE INDEX CONCURRENTLY orders_user_id_idx ON orders(user_id);

-- Safe FK: add without validating existing rows first
ALTER TABLE orders ADD CONSTRAINT orders_user_fk
  FOREIGN KEY (user_id) REFERENCES users(id) NOT VALID;
-- Then validate separately (ShareUpdateExclusiveLock only)
ALTER TABLE orders VALIDATE CONSTRAINT orders_user_fk;

DML — CRUD Operations
INSERT, UPDATE, DELETE, UPSERT, RETURNING, COPY
SQLAdvanced DML patterns
── INSERT with RETURNING ──────────────────────────────
INSERT INTO users (email, username)
VALUES ('alice@example.com', 'alice')
RETURNING id, created_at;

── Bulk INSERT (best performance with COPY) ───────────
INSERT INTO orders (user_id, total)
SELECT id, (random() * 1000)::numeric(10,2)
FROM generate_series(1, 100000) AS id;

── UPSERT — ON CONFLICT ───────────────────────────────
INSERT INTO users (email, username)
VALUES ('bob@example.com', 'bob')
ON CONFLICT (email) DO UPDATE SET
  username   = EXCLUDED.username,
  updated_at = now()
RETURNING id, (xmax = 0) AS was_inserted;

── UPDATE with JOIN (using FROM clause) ──────────────
UPDATE orders o
SET    total = o.total * 1.1
FROM   users u
WHERE  u.id = o.user_id
  AND  u.status = 'vip'
RETURNING o.id, o.total;

── DELETE with RETURNING ──────────────────────────────
WITH deleted AS (
  DELETE FROM orders
  WHERE created_at < now() - '1 year'::interval
  RETURNING *
)
INSERT INTO orders_archive SELECT * FROM deleted;

── COPY — fastest bulk load ───────────────────────────
COPY orders (user_id, total) FROM '/data/orders.csv' CSV HEADER;
-- From stdin (app-level)
COPY orders TO STDOUT WITH (FORMAT binary);

Querying — SELECT Deep Dive
Filtering, sorting, LIMIT, OFFSET, FETCH, DISTINCT, GROUPING SETS
SQLAdvanced SELECT patterns
── Keyset pagination (efficient, no OFFSET degradation) ─
SELECT id, email, created_at
FROM   users
WHERE  (created_at, id) < ('2024-06-01'::timestamptz, 9999)
ORDER BY created_at DESC, id DESC
LIMIT 20;

── GROUPING SETS / CUBE / ROLLUP ─────────────────────
SELECT
  date_trunc('month', created_at) AS month,
  status,
  sum(total) AS revenue
FROM   orders
GROUP BY ROLLUP (date_trunc('month', created_at), status)
ORDER BY 1, 2;

── DISTINCT ON (PostgreSQL-specific, very useful) ────
SELECT DISTINCT ON (user_id)
  user_id, id AS latest_order_id, total, created_at
FROM   orders
ORDER BY user_id, created_at DESC;

── FILTER in aggregates ──────────────────────────────
SELECT
  count(*) FILTER (WHERE status = 'shipped')   AS shipped,
  count(*) FILTER (WHERE status = 'pending')   AS pending,
  sum(total) FILTER (WHERE total > 500)         AS high_value_revenue
FROM orders;

Joins & Set Operations
JOIN types, LATERAL, set operators, anti-joins
SQLJoin patterns every senior dev should know
── Anti-join (users with NO orders) ─────────────────
-- Preferred over NOT IN (NULL-safe) and usually fastest
SELECT u.*
FROM   users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE  o.id IS NULL;

── LATERAL JOIN — correlated subquery as join ────────
SELECT u.id, u.email, last_order.*
FROM   users u
LEFT JOIN LATERAL (
  SELECT id, total, created_at
  FROM   orders
  WHERE  user_id = u.id
  ORDER BY created_at DESC
  LIMIT 1
) last_order ON TRUE;

── Self-join (hierarchical / org tree) ──────────────
SELECT e.name AS employee, m.name AS manager
FROM   employees e
LEFT JOIN employees m ON m.id = e.manager_id;

── CROSS JOIN LATERAL with generate_series ───────────
SELECT d::date
FROM   generate_series(
  '2024-01-01'::date,
  '2024-12-31'::date,
  '1 day'::interval
) d;

── Set operations ────────────────────────────────────
SELECT email FROM users
INTERSECT
SELECT email FROM newsletter_subscribers;

SELECT email FROM users
EXCEPT
SELECT email FROM blocked_users;
07
Aggregates & Window Functions
GROUP BY, HAVING, OVER, PARTITION BY, FRAME clauses
SQLWindow functions — the most powerful SQL feature
── Anatomy of a window function ─────────────────────
function_name(args) OVER (
  [PARTITION BY partition_expr]
  [ORDER BY sort_expr]
  [ROWS|RANGE|GROUPS BETWEEN frame_start AND frame_end]
)

── Ranking functions ─────────────────────────────────
SELECT
  user_id, total,
  rank()         OVER w AS rnk,         -- gaps on ties
  dense_rank()   OVER w AS drnk,        -- no gaps
  row_number()   OVER w AS rn,           -- always unique
  ntile(4)       OVER w AS quartile,    -- bucket (1-4)
  percent_rank() OVER w AS pct_rank
FROM  orders
WINDOW w AS (PARTITION BY user_id ORDER BY total DESC);

── Running totals & moving avg ───────────────────────
SELECT
  created_at::date,
  sum(total) AS daily_rev,
  sum(sum(total)) OVER (ORDER BY created_at::date)
    AS cumulative_rev,
  avg(sum(total)) OVER (
    ORDER BY created_at::date
    ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
  ) AS rolling_7d_avg
FROM   orders
GROUP BY created_at::date
ORDER BY 1;

── LAG / LEAD — access adjacent rows ─────────────────
SELECT
  user_id,
  total,
  created_at,
  lag(total, 1) OVER (PARTITION BY user_id ORDER BY created_at)
    AS prev_order_total,
  total - lag(total, 1) OVER (PARTITION BY user_id ORDER BY created_at)
    AS change_from_prev
FROM orders;

── FIRST_VALUE / LAST_VALUE / NTH_VALUE ─────────────
SELECT
  id,
  total,
  first_value(total) OVER (PARTITION BY user_id
    ORDER BY created_at
    ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
  ) AS first_order_total
FROM orders;

SQLIndex design patterns
── Covering index (index-only scan, no heap access) ──
CREATE INDEX orders_user_date_covering_idx
  ON orders(user_id, created_at DESC)
  INCLUDE (total, status);  -- stored but not part of key

── Partial index (only index rows you query) ─────────
CREATE INDEX orders_pending_idx
  ON orders(created_at)
  WHERE status = 'pending';

── Expression index ──────────────────────────────────
CREATE INDEX users_email_lower_idx
  ON users(lower(email));
-- Query MUST use same expression:
SELECT * FROM users WHERE lower(email) = 'alice@example.com';

── GIN index for JSONB ───────────────────────────────
CREATE INDEX users_metadata_gin
  ON users USING gin(metadata);
SELECT * FROM users WHERE metadata @> '{"plan":"pro"}';

── BRIN for time-series ──────────────────────────────
CREATE INDEX events_at_brin
  ON events USING brin(event_at) WITH (pages_per_range=128);

── Diagnose unused indexes ───────────────────────────
SELECT schemaname, relname, indexrelname, idx_scan
FROM   pg_stat_user_indexes
WHERE  idx_scan = 0
ORDER BY pg_relation_size(indexrelid) DESC;

Isolation levels, locking, advisory locks, deadlocks

Isolation Levels

READ UNCOMMITTED❌ Possible*❌❌❌
READ COMMITTED (default)✅ Safe❌ Possible❌❌

* PostgreSQL doesn't actually allow dirty reads even at READ UNCOMMITTED.

SQLTransaction & locking patterns
── Explicit transaction ──────────────────────────────
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;

── Serializable (SSI) — true serializability ─────────
BEGIN ISOLATION LEVEL SERIALIZABLE;
-- PG detects serialization anomalies and rolls back

── SELECT FOR UPDATE — pessimistic locking ───────────
SELECT * FROM inventory
WHERE  product_id = 42
FOR UPDATE;                     -- blocks other writers

SELECT * FROM inventory
FOR UPDATE SKIP LOCKED;         -- job queue pattern!

SELECT * FROM inventory
FOR SHARE;                      -- allow other readers

── Advisory locks (application-level mutex) ──────────
SELECT pg_advisory_lock(12345);         -- blocks
SELECT pg_try_advisory_lock(12345);     -- non-blocking
SELECT pg_advisory_unlock(12345);       -- release
-- Session-scoped: auto-released on disconnect
SELECT pg_advisory_xact_lock(12345);   -- tx-scoped

── Detect & kill long-running locks ──────────────────
SELECT pid, now() - pg_stat_activity.query_start AS duration, query
FROM   pg_stat_activity
WHERE  state = 'active'
  AND  now() - pg_stat_activity.query_start > '5 minutes'::interval;

SELECT pg_terminate_backend(pid);

Deadlock Detection

Postgres auto-detects deadlocks (deadlock_timeout default 1s) and rolls back one transaction. Prevent by always acquiring locks in the same order across transactions.

🔴

Always order your UPDATE/SELECT FOR UPDATE statements consistently across transactions to prevent deadlocks. Never hold a transaction open while waiting for user input.

Views, CTEs & Subqueries
Materialized views, recursive CTEs, lateral subqueries
SQLCTEs, recursive queries, materialized views
── Recursive CTE — org tree / graph traversal ────────
WITH RECURSIVE org_tree AS (
  -- Anchor: top-level employees
  SELECT id, name, manager_id, 0 AS depth, ARRAY[id] AS path
  FROM   employees
  WHERE  manager_id IS NULL

  UNION ALL

  -- Recursive: children
  SELECT e.id, e.name, e.manager_id, o.depth + 1, o.path || e.id
  FROM   employees e
  JOIN   org_tree o ON o.id = e.manager_id
  WHERE  NOT (e.id = ANY(o.path))  -- cycle guard
)
SELECT repeat('  ', depth) || name AS tree, depth
FROM   org_tree
ORDER BY path;

── Materialized View ─────────────────────────────────
CREATE MATERIALIZED VIEW monthly_revenue AS
  SELECT
    date_trunc('month', created_at) AS month,
    sum(total) AS revenue,
    count(*) AS order_count
  FROM  orders
  GROUP BY 1
WITH DATA;

CREATE UNIQUE INDEX ON monthly_revenue(month);

-- Non-blocking refresh
REFRESH MATERIALIZED VIEW CONCURRENTLY monthly_revenue;

── Updatable View ────────────────────────────────────
CREATE VIEW active_users AS
  SELECT * FROM users WHERE status != 'deleted'
  WITH CHECK OPTION;  -- prevent inserting deleted users

── CTE as data pipeline ──────────────────────────────
WITH
  base AS (SELECT * FROM orders WHERE created_at > now() - '30 days'::interval),
  enriched AS (
    SELECT b.*, u.email
    FROM base b JOIN users u ON u.id = b.user_id
  ),
  ranked AS (
    SELECT *, rank() OVER (ORDER BY total DESC) AS rnk
    FROM enriched
  )
SELECT * FROM ranked WHERE rnk <= 10;

Table Partitioning
Range, list, hash partitioning — declarative partitioning
SQLDeclarative partitioning (PG 10+)
── Range partitioning (e.g., by month) ───────────────
CREATE TABLE events (
  id         bigint NOT NULL,
  event_at   timestamptz NOT NULL,
  payload    jsonb
) PARTITION BY RANGE (event_at);

CREATE TABLE events_2024_01 PARTITION OF events
  FOR VALUES FROM ('2024-01-01') TO ('2024-02-01');

CREATE TABLE events_2024_02 PARTITION OF events
  FOR VALUES FROM ('2024-02-01') TO ('2024-03-01');

-- Default partition for out-of-range rows
CREATE TABLE events_default PARTITION OF events DEFAULT;

── Hash partitioning (even distribution) ────────────
CREATE TABLE sessions (
  session_id uuid NOT NULL,
  data       jsonb
) PARTITION BY HASH (session_id);

CREATE TABLE sessions_0 PARTITION OF sessions
  FOR VALUES WITH (MODULUS 4, REMAINDER 0);
CREATE TABLE sessions_1 PARTITION OF sessions
  FOR VALUES WITH (MODULUS 4, REMAINDER 1);
-- ... sessions_2, sessions_3

── Partition pruning verification ────────────────────
EXPLAIN SELECT * FROM events
WHERE  event_at BETWEEN '2024-01-01' AND '2024-01-31';
-- Should show only events_2024_01 in plan

── Detach old partition (instant, non-blocking) ──────
ALTER TABLE events DETACH PARTITION events_2024_01 CONCURRENTLY;

Functions & Stored Procedures
PL/pgSQL, set-returning, security definer, procedures with COMMIT
PL/pgSQLFunctions & procedures
── Scalar function ───────────────────────────────────
CREATE OR REPLACE FUNCTION get_user_order_count(p_user_id bigint)
RETURNS bigint
LANGUAGE sql STABLE PARALLEL SAFE  -- hints for planner
AS $$
  SELECT count(*) FROM orders WHERE user_id = p_user_id;
$$;

── PL/pgSQL with exception handling ─────────────────
CREATE OR REPLACE FUNCTION transfer_funds(
  from_id bigint, to_id bigint, amount numeric
)
RETURNS void LANGUAGE plpgsql AS $$
DECLARE
  v_balance numeric;
BEGIN
  SELECT balance INTO STRICT v_balance
  FROM   accounts WHERE id = from_id FOR UPDATE;

  IF v_balance < amount THEN
    RAISE EXCEPTION 'Insufficient funds: balance=%, needed=%',
      v_balance, amount;
  END IF;

  UPDATE accounts SET balance = balance - amount WHERE id = from_id;
  UPDATE accounts SET balance = balance + amount WHERE id = to_id;
EXCEPTION
  WHEN NO_DATA_FOUND THEN
    RAISE EXCEPTION 'Account not found';
END;
$$;

── Set-returning function (SRF) ──────────────────────
CREATE OR REPLACE FUNCTION get_user_orders(p_user_id bigint)
RETURNS SETOF orders
LANGUAGE sql STABLE AS $$
  SELECT * FROM orders WHERE user_id = p_user_id;
$$;

── Stored Procedure (PG11+) — can COMMIT mid-proc ───
CREATE OR REPLACE PROCEDURE batch_process_orders(batch_size int)
LANGUAGE plpgsql AS $$
DECLARE r orders%ROWTYPE;
BEGIN
  FOR r IN SELECT * FROM orders WHERE status='pending'
             LIMIT batch_size FOR UPDATE SKIP LOCKED
  LOOP
    -- process...
    UPDATE orders SET status='processing' WHERE id=r.id;
    COMMIT;  -- commit each row (only in PROCEDURE)
  END LOOP;
END;
$$;

CALL batch_process_orders(1000);

Triggers
Row-level, statement-level, INSTEAD OF, event triggers
PL/pgSQLTrigger patterns
── Auto-update updated_at ────────────────────────────
CREATE OR REPLACE FUNCTION set_updated_at()
RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  NEW.updated_at = now();
  RETURN NEW;
END;
$$;

CREATE TRIGGER users_updated_at
  BEFORE UPDATE ON users
  FOR EACH ROW EXECUTE FUNCTION set_updated_at();

── Audit log trigger ─────────────────────────────────
CREATE TABLE audit_log (
  id        bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  tbl       text,
  op        text,
  old_data  jsonb,
  new_data  jsonb,
  changed_by text DEFAULT current_user,
  changed_at timestamptz DEFAULT now()
);

CREATE OR REPLACE FUNCTION audit_trigger()
RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  INSERT INTO audit_log(tbl, op, old_data, new_data)
  VALUES (
    TG_TABLE_NAME, TG_OP,
    CASE WHEN TG_OP IN ('UPDATE','DELETE') THEN to_jsonb(OLD) END,
    CASE WHEN TG_OP IN ('UPDATE','INSERT') THEN to_jsonb(NEW) END
  );
  RETURN COALESCE(NEW, OLD);
END;
$$;

CREATE TRIGGER orders_audit
  AFTER INSERT OR UPDATE OR DELETE ON orders
  FOR EACH ROW EXECUTE FUNCTION audit_trigger();

── Event trigger (DDL changes) ───────────────────────
CREATE OR REPLACE FUNCTION log_ddl()
RETURNS event_trigger LANGUAGE plpgsql AS $$
BEGIN
  RAISE NOTICE 'DDL command: %', tg_tag;
END;
$$;
CREATE EVENT TRIGGER ddl_logger ON ddl_command_start
  EXECUTE FUNCTION log_ddl();

JSON & JSONB
Operators, path queries, aggregation, jsonpath (PG12+)
SQLJSONB operators & functions
── Operators ─────────────────────────────────────────
SELECT metadata -> 'plan'           FROM users;  -- JSON value
SELECT metadata ->> 'plan'          FROM users;  -- text value
SELECT metadata #> '{address,city}' FROM users;  -- nested JSON
SELECT metadata @> '{"plan":"pro"}' FROM users;  -- contains
SELECT metadata ? 'plan'             FROM users;  -- key exists
SELECT metadata ?| ARRAY['plan','tier'] FROM users; -- any key

── Merge / update JSONB ──────────────────────────────
UPDATE users
SET    metadata = metadata || '{"verified": true}'::jsonb
WHERE  id = 42;

-- Remove key
UPDATE users SET metadata = metadata - 'temp_token';

── jsonb_set for nested updates ──────────────────────
UPDATE users
SET    metadata = jsonb_set(metadata, '{address,city}', '"Mumbai"')
WHERE  id = 42;

── jsonpath (PG12+) ──────────────────────────────────
SELECT * FROM users
WHERE  metadata @@ '$.tags[*] == "premium"';

SELECT jsonb_path_query(metadata, '$.orders[*].total ? (@ > 100)')
FROM   users;

── Aggregate JSON ────────────────────────────────────
SELECT
  user_id,
  jsonb_agg(jsonb_build_object(
    'id', id, 'total', total, 'date', created_at
  ) ORDER BY created_at) AS orders_json
FROM  orders
GROUP BY user_id;

── Expand JSON array to rows ─────────────────────────
SELECT u.id, tag
FROM   users u,
       jsonb_array_elements_text(metadata->'tags') AS tag;

Replication & High Availability
Streaming, logical replication, WAL, Patroni, failover
Physical (Streaming) Replication

Binary WAL stream. Replica is exact byte-for-byte copy. Best for HA standby and read replicas. Synchronous or asynchronous.

Logical Replication

Row-level changes via publication/subscription. Can replicate specific tables across versions or to different schemas. Used for zero-downtime upgrades.

Patroni

HA framework using etcd/Consul/ZooKeeper for leader election. Auto-failover with configurable sync modes. Industry standard for production Postgres HA.

WAL Archiving (PITR)

Archive WAL segments to S3/GCS. Combined with base backups enables Point-in-Time Recovery to any moment.

SQL + CONFIGReplication setup
── postgresql.conf (primary) ─────────────────────────
wal_level = logical          -- or replica for streaming only
max_wal_senders = 10
max_replication_slots = 10
synchronous_commit = on      -- or remote_write / remote_apply

── Create replication slot (prevents WAL deletion) ───
SELECT * FROM pg_create_physical_replication_slot('replica1');
SELECT * FROM pg_create_logical_replication_slot('my_slot', 'pgoutput');

── Logical replication pub/sub ───────────────────────
-- On source:
CREATE PUBLICATION my_pub FOR TABLE orders, users;

-- On target:
CREATE SUBSCRIPTION my_sub
  CONNECTION 'host=primary dbname=mydb user=replicator'
  PUBLICATION my_pub;

── Role-based access control ─────────────────────────
CREATE ROLE app_readonly;
GRANT CONNECT ON DATABASE mydb TO app_readonly;

  GRANT SELECT ON TABLES TO app_readonly;

CREATE ROLE app_user LOGIN PASSWORD '...' IN ROLE app_readonly;

── Row-Level Security (RLS) ──────────────────────────
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;

-- Users can only see their own orders
CREATE POLICY orders_isolation ON orders
  USING (user_id = current_setting('app.current_user_id')::bigint);

-- Set at connection time:
SET app.current_user_id = '42';
SELECT * FROM orders;  -- only returns user 42's orders

-- Bypass RLS for service role
ALTER TABLE orders FORCE ROW LEVEL SECURITY;
CREATE ROLE service_role BYPASSRLS;

── Column-level privileges ───────────────────────────
REVOKE ALL ON users FROM app_user;
GRANT SELECT (id, email, username) ON users TO app_user;

CREATE FUNCTION get_sensitive_data()
RETURNS TABLE(id bigint, email text)
LANGUAGE sql SECURITY DEFINER
SET search_path = public  -- prevent search_path injection!

Backup, Restore & PITR
pg_dump, pg_basebackup, WAL-E/pgBackRest, point-in-time recovery
BASH + SQLBackup & recovery commands
# ── Logical backup (pg_dump) ──────────────────────────
pg_dump -Fc -Z9 -j4 mydb > mydb.dump         # custom format, compressed, 4 parallel jobs
pg_dump -Fd -j8 -f /backups/mydb mydb         # directory format for parallel restore
pg_dump --table=orders mydb > orders.sql      # single table

# Restore
pg_restore -Fc -j4 -d mydb_restore mydb.dump
psql -d newdb < schema.sql

# ── Physical backup (streaming) ───────────────────────
pg_basebackup -h primary -U replicator \
  -D /var/lib/postgresql/backup \
  -Ft -z -P -Xs              # tar, gzip, progress, stream WAL

# ── pgBackRest (production tool) ─────────────────────
pgbackrest --stanza=mydb backup --type=full
pgbackrest --stanza=mydb backup --type=incr
pgbackrest --stanza=mydb restore \
  --target="2024-06-15 14:30:00" \
  --target-action=promote

── PITR via recovery.conf (PG11 and earlier) ─────────
-- In postgresql.conf (PG12+):
restore_command = 'cp /wal_archive/%f %p'
recovery_target_time = '2024-06-15 14:30:00 UTC'
recovery_target_action = 'promote'

── Active queries ────────────────────────────────────
SELECT pid, usename, application_name, state,
  now() - query_start AS duration, query
FROM   pg_stat_activity
WHERE  state != 'idle'
ORDER BY duration DESC;

── Lock waits ────────────────────────────────────────
SELECT
  blocked.pid, blocked.query,
  blocking.pid AS blocking_pid, blocking.query AS blocking_query
FROM   pg_stat_activity blocked
JOIN   pg_stat_activity blocking
  ON   blocking.pid = ANY(pg_blocking_pids(blocked.pid))
WHERE  blocked.wait_event_type = 'Lock';

── Cache hit ratio (should be > 99%) ─────────────────
SELECT
  sum(heap_blks_hit) * 100.0 /
  nullif(sum(heap_blks_hit) + sum(heap_blks_read), 0) AS cache_hit_pct
FROM   pg_statio_user_tables;

── Index hit ratio (should be > 99%) ────────────────
SELECT
  sum(idx_blks_hit) * 100.0 /
  nullif(sum(idx_blks_hit) + sum(idx_blks_read), 0) AS idx_hit_pct
FROM   pg_statio_user_indexes;
