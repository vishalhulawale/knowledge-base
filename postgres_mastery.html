Architecture & Internals
How PostgreSQL works under the hood — processes, memory, storage

Process Model

PostgreSQL uses a multi-process model (not multi-threaded). Each client connection spawns a dedicated backend process. The postmaster is the main daemon that manages lifecycle. This design means a crash in one backend can't corrupt memory of other backends — but it also means each connection costs an OS process (~5–10 MB RAM), making connection pooling essential at scale.

🏠 Postmaster

The parent process. Listens for connections, forks backend processes, manages shared memory init.

⚙️ Backend Process

One per client. Executes queries, holds locks, manages its own portal and memory context.

♻️ Background Workers

Autovacuum, WAL writer, checkpointer, bgwriter, stats collector, logical replication workers.

📝 WAL Writer

Flushes WAL (Write-Ahead Log) buffers to disk. Critical for durability — data is written to WAL before heap.

Storage Layout

Every table and index is stored as a set of 8 KB pages (blocks). Each page has a header, item pointers (line pointers), and tuple data.

SQLInspect page internals
-- Install pageinspect extension
CREATE EXTENSION pageinspect;

-- View raw page header
SELECT * FROM page_header(get_raw_page('orders', 0));

-- View heap tuples on page 0
SELECT t_ctid, t_infomask, t_data
FROM heap_page_items(get_raw_page('orders', 0));

-- MVCC: each row has xmin/xmax to track visibility
SELECT xmin, xmax, ctid, * FROM orders LIMIT 5;

WAL — Write-Ahead Log

Every data modification is first written to the WAL (an append-only sequential log on disk), then applied to heap pages in shared_buffers. On crash, Postgres replays WAL from the last checkpoint to recover. This guarantees durability (the D in ACID) even if the server crashes mid-write. WAL is organized into 16 MB segments and is also the basis for both streaming and logical replication.

Checkpoints flush dirty shared_buffer pages to disk and write a checkpoint record to WAL. They limit crash recovery time by bounding how much WAL must be replayed. checkpoint_completion_target = 0.9 spreads the flush I/O over 90% of the checkpoint interval to avoid I/O spikes. max_wal_size controls how much WAL can accumulate before forcing a checkpoint.

MVCC — Multi-Version Concurrency Control

PostgreSQL never overwrites rows in place. Each UPDATE inserts a new row version and marks the old one dead by stamping its xmax with the updating transaction's ID. xmin is set when the row is created. A row is visible to a transaction only if xmin is committed and < the transaction's snapshot, and xmax is either not committed or > the snapshot. This is how multiple concurrent readers each see a consistent, point-in-time view with zero locking.

Dead tuples accumulate over time (every UPDATE leaves a dead version) and are cleaned by VACUUM. Transaction ID wraparound (the 32-bit XID counter cycling) is a real production risk — monitor age(datfrozenxid) and ensure autovacuum freezes old tuples before XID age approaches 2 billion.

💡

MVCC means readers never block writers and writers never block readers — the foundation of Postgres concurrency. This is fundamentally different from MySQL's InnoDB undo-log MVCC model.

SQLMVCC visibility
-- Check transaction ID age — important for wraparound prevention
SELECT datname, age(datfrozenxid) AS xid_age
FROM pg_database
ORDER BY xid_age DESC;

-- Tables with many dead tuples (need VACUUM)
SELECT relname, n_dead_tup, n_live_tup,
       round(n_dead_tup::numeric/nullif(n_live_tup+n_dead_tup,0)*100,2) AS dead_pct
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;

Data Types
Rich type system — choose wisely, performance depends on it

Type Selection Principles

Choosing the right type affects storage efficiency, index size, query performance, and correctness. Critical distinctions that come up in interviews:

  • text vs varchar(n): Functionally identical in PostgreSQL — both use the same storage engine (TOAST for large values). A length limit in varchar(n) is enforced at write time but provides no performance or storage benefit. Prefer text with a CHECK(length(...) <= n) constraint for flexibility.
  • timestamptz vs timestamp: timestamptz stores UTC internally and converts to/from the session timezone on display. timestamp stores the literal value with no timezone — a footgun for any multi-timezone application. Always use timestamptz for application data.
  • numeric vs float: float/double precision uses binary floating point — 0.1 + 0.2 ≠ 0.3. numeric(p,s) is exact decimal arithmetic, slower but correct. Always use numeric for money, and anything requiring exact decimal arithmetic.
  • uuid vs bigint: UUIDs (16 bytes) are globally unique with no coordination — safe for distributed ID generation. But random UUIDs (v4) cause B-tree index fragmentation at high insert rates. Use UUIDv7 (time-ordered) or bigint IDENTITY sequences for high-write tables.
  • GENERATED ALWAYS AS IDENTITY vs serial: serial is syntactic sugar that creates a sequence and sets a default — it's not a real type. GENERATED ALWAYS AS IDENTITY (SQL standard, PG10+) is explicit about generation intent and prevents accidental inserts of arbitrary values. Prefer IDENTITY for all new schemas.

DDL — Schema Design
Tables, constraints, sequences, schemas, inheritance

Schema Design Principles

Good schema design is the highest-leverage decision in a PostgreSQL system — bad schemas require expensive migrations, cause query plan problems, and limit scalability. Key principles:

  • Constraints are documentation + correctness: NOT NULL, UNIQUE, CHECK, and FK constraints are enforced at the database level, not just the application. They also give the query planner stronger guarantees, enabling better optimizations.
  • Foreign Key locking: FK references hold a ROW SHARE lock on the referenced row during the transaction. ON DELETE CASCADE is convenient but can cause surprising performance on mass deletes. Consider soft deletes or explicit child deletion for large datasets.
  • Generated columns (PG12+) are computed and stored — they're always consistent with the source columns and can be indexed like regular columns. Useful for computed keys (e.g., lower(email) for case-insensitive lookups).
⚠️

Zero-downtime migrations: Most ALTER TABLE operations take an ACCESS EXCLUSIVE lock, blocking all reads and writes on the table. On a 100M-row table, even a millisecond operation causes queued queries to pile up. Always use CREATE INDEX CONCURRENTLY, ADD COLUMN … NOT VALID + VALIDATE CONSTRAINT separately, and pg_repack for table rewrites.

Table Creation & Constraints

SQLProduction-grade table design
CREATE TABLE users (
  id          bigint      GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email       text        NOT NULL UNIQUE,
  username    text        NOT NULL
              CHECK (length(username) BETWEEN 3 AND 50),
  status      order_status NOT NULL DEFAULT 'pending',
  metadata    jsonb       NOT NULL DEFAULT '{}',
  created_at  timestamptz NOT NULL DEFAULT now(),
  updated_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE orders (
  id          bigint      GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id     bigint      NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  total       numeric(12,2) NOT NULL CHECK (total >= 0),
  created_at  timestamptz NOT NULL DEFAULT now()
);

-- Partial unique index (unique email per active users only)
CREATE UNIQUE INDEX users_email_active_uidx
  ON users(email) WHERE status != 'deleted';

-- Generated column (computed, stored)
ALTER TABLE users ADD COLUMN
  email_domain text GENERATED ALWAYS AS (
    split_part(email, '@', 2)
  ) STORED;

ALTER TABLE — Zero-Downtime Patterns

⚠️

Many ALTER TABLE operations take an ACCESS EXCLUSIVE lock. On large tables, use pg_repack, concurrent index builds, and careful column additions.

SQLSafe schema migrations
-- Safe: add nullable column (no default = instant)
ALTER TABLE orders ADD COLUMN notes text;

-- Safe in PG11+: add column with default (no rewrite!)
ALTER TABLE orders ADD COLUMN priority int NOT NULL DEFAULT 0;

-- Safe: build index without blocking reads/writes
CREATE INDEX CONCURRENTLY orders_user_id_idx ON orders(user_id);

-- Safe FK: add without validating existing rows first
ALTER TABLE orders ADD CONSTRAINT orders_user_fk
  FOREIGN KEY (user_id) REFERENCES users(id) NOT VALID;
-- Then validate separately (ShareUpdateExclusiveLock only)
ALTER TABLE orders VALIDATE CONSTRAINT orders_user_fk;

DML — CRUD Operations
INSERT, UPDATE, DELETE, UPSERT, RETURNING, COPY

DML Core Concepts

RETURNING eliminates a round-trip: instead of INSERT then SELECT, you get back generated IDs, defaults, or any column in a single network call. Essential for high-throughput APIs. RETURNING works on INSERT, UPDATE, and DELETE.

UPSERT (ON CONFLICT) is atomic at the row level — no race condition between the SELECT-then-INSERT pattern. The EXCLUDED pseudo-table holds the values that would have been inserted. Use ON CONFLICT DO NOTHING to silently skip duplicates. Use (xmax = 0) AS was_inserted in RETURNING to distinguish inserts from updates — xmax is 0 for freshly inserted rows.

UPDATE … FROM is PostgreSQL's join-based update — far more efficient than a correlated subquery UPDATE … SET x = (SELECT …). The FROM clause participates in a single hash/merge join, not a per-row subquery execution.

Writable CTEs (WITH … DELETE/INSERT) execute atomically as a single statement. The classic archive pattern — DELETE returning rows, then INSERT into archive — is safe and consistent within one transaction without extra locking.

💡

COPY is 10–100× faster than INSERT for bulk loads — it bypasses the expression evaluator, uses binary protocol, defers constraint checks, and minimizes WAL traffic. Use COPY FROM STDIN with binary format from application code (e.g., pgx CopyFrom in Go, psycopg2 copy_from in Python) for maximum ingestion throughput.

SQLAdvanced DML patterns
── INSERT with RETURNING ──────────────────────────────
INSERT INTO users (email, username)
VALUES ('alice@example.com', 'alice')
RETURNING id, created_at;

── Bulk INSERT (best performance with COPY) ───────────
INSERT INTO orders (user_id, total)
SELECT id, (random() * 1000)::numeric(10,2)
FROM generate_series(1, 100000) AS id;

── UPSERT — ON CONFLICT ───────────────────────────────
INSERT INTO users (email, username)
VALUES ('bob@example.com', 'bob')
ON CONFLICT (email) DO UPDATE SET
  username   = EXCLUDED.username,
  updated_at = now()
RETURNING id, (xmax = 0) AS was_inserted;

── UPDATE with JOIN (using FROM clause) ──────────────
UPDATE orders o
SET    total = o.total * 1.1
FROM   users u
WHERE  u.id = o.user_id
  AND  u.status = 'vip'
RETURNING o.id, o.total;

── DELETE with RETURNING ──────────────────────────────
WITH deleted AS (
  DELETE FROM orders
  WHERE created_at < now() - '1 year'::interval
  RETURNING *
)
INSERT INTO orders_archive SELECT * FROM deleted;

── COPY — fastest bulk load ───────────────────────────
COPY orders (user_id, total) FROM '/data/orders.csv' CSV HEADER;
-- From stdin (app-level)
COPY orders TO STDOUT WITH (FORMAT binary);

Querying — SELECT Deep Dive
Filtering, sorting, LIMIT, OFFSET, FETCH, DISTINCT, GROUPING SETS

Advanced Query Mechanics

Keyset pagination (cursor-based) uses a compound WHERE predicate on indexed columns: WHERE (created_at, id) < (prev_created_at, prev_id). It stays O(log n) regardless of page depth because the planner uses the index to jump directly to the cursor position. OFFSET-based pagination degrades linearly — page 1000 requires scanning and discarding 999 × page_size rows. At scale, high-offset queries are full table scans in disguise.

ROLLUP vs CUBE vs GROUPING SETS all produce multi-level aggregations in one pass:

  • ROLLUP(a, b) produces groupings: (a, b), (a), () — left-to-right subtotals + grand total. Perfect for hierarchical reports (year → month → day).
  • CUBE(a, b) produces all 2ⁿ combinations: (a, b), (a), (b), () — every possible cross-tab subtotal.
  • GROUPING SETS((a,b),(a),()) — explicit control over exactly which groupings you need. NULL in the result means "aggregated across that dimension"; use GROUPING(col) to distinguish NULL-as-grouping from NULL-as-data.

DISTINCT ON is PostgreSQL-specific and maps to a single Unique plan node — cheaper than a window function for "first row per group." The ORDER BY must start with the DISTINCT ON columns; the rest of ORDER BY controls which row is "first" within each group.

FILTER in aggregates replaces the verbose SUM(CASE WHEN … END) pattern. It's cleaner and allows the planner to optimize each condition independently. Multiple filtered aggregates over the same table scan in one pass — no subqueries needed.

SQLAdvanced SELECT patterns
── Keyset pagination (efficient, no OFFSET degradation) ─
SELECT id, email, created_at
FROM   users
WHERE  (created_at, id) < ('2024-06-01'::timestamptz, 9999)
ORDER BY created_at DESC, id DESC
LIMIT 20;

── GROUPING SETS / CUBE / ROLLUP ─────────────────────
SELECT
  date_trunc('month', created_at) AS month,
  status,
  sum(total) AS revenue
FROM   orders
GROUP BY ROLLUP (date_trunc('month', created_at), status)
ORDER BY 1, 2;

── DISTINCT ON (PostgreSQL-specific, very useful) ────
SELECT DISTINCT ON (user_id)
  user_id, id AS latest_order_id, total, created_at
FROM   orders
ORDER BY user_id, created_at DESC;

── FILTER in aggregates ──────────────────────────────
SELECT
  count(*) FILTER (WHERE status = 'shipped')   AS shipped,
  count(*) FILTER (WHERE status = 'pending')   AS pending,
  sum(total) FILTER (WHERE total > 500)         AS high_value_revenue
FROM orders;

Joins & Set Operations
JOIN types, LATERAL, set operators, anti-joins

Join Mechanics & Physical Algorithms

PostgreSQL chooses between three physical join algorithms based on cost estimates:

  • Nested Loop: For each outer row, scan the inner relation. O(n×m) worst case. Best when the inner relation is small or accessed via an index (Index Nested Loop). The planner prefers this for selective joins with a good inner index.
  • Hash Join: Build an in-memory hash table on the smaller (inner) relation, then probe with each outer row. O(n+m). Best for large unsorted relations — dominant algorithm for analytical joins. Limited by work_mem; if hash table exceeds work_mem it spills to disk in batches.
  • Merge Join: Requires both inputs sorted on the join key (from an index or explicit Sort node). Very efficient when both inputs arrive pre-sorted. Preferred when sorted output is also needed downstream.

Anti-join: Finding rows in A with no matching rows in B. The LEFT JOIN … WHERE b.id IS NULL pattern is NULL-safe and compiles to an anti-join plan node (equivalent to NOT EXISTS). Avoid NOT IN (SELECT …) — if the subquery returns any NULL, the entire NOT IN returns zero rows due to three-valued logic. This is a classic interview trap.

LATERAL JOIN is a correlated subquery promoted to a join position. The subquery can reference columns from tables to its left — like a for-each loop that executes a subquery per outer row, but implemented as a join. Key use case: "for each user, get their 3 most recent orders" without window functions. The ON TRUE is required because LATERAL produces rows, not a scalar.

💡

UNION vs UNION ALL: UNION deduplicates (sort + unique step, O(n log n)). UNION ALL concatenates without dedup. Always use UNION ALL unless deduplication is explicitly required. INTERSECT and EXCEPT have ALL variants too. Set operations require matching column counts and compatible types.

SQLJoin patterns every senior dev should know
── Anti-join (users with NO orders) ─────────────────
-- Preferred over NOT IN (NULL-safe) and usually fastest
SELECT u.*
FROM   users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE  o.id IS NULL;

── LATERAL JOIN — correlated subquery as join ────────
SELECT u.id, u.email, last_order.*
FROM   users u
LEFT JOIN LATERAL (
  SELECT id, total, created_at
  FROM   orders
  WHERE  user_id = u.id
  ORDER BY created_at DESC
  LIMIT 1
) last_order ON TRUE;

── Self-join (hierarchical / org tree) ──────────────
SELECT e.name AS employee, m.name AS manager
FROM   employees e
LEFT JOIN employees m ON m.id = e.manager_id;

── CROSS JOIN LATERAL with generate_series ───────────
SELECT d::date
FROM   generate_series(
  '2024-01-01'::date,
  '2024-12-31'::date,
  '1 day'::interval
) d;

── Set operations ────────────────────────────────────
SELECT email FROM users
INTERSECT
SELECT email FROM newsletter_subscribers;

SELECT email FROM users
EXCEPT
SELECT email FROM blocked_users;

Aggregates & Window Functions
GROUP BY, HAVING, OVER, PARTITION BY, FRAME clauses

Window Function Architecture

Window functions compute a value across a window of rows related to the current row, without collapsing rows like GROUP BY does. Critical execution-order fact: window functions run after WHERE, GROUP BY, and HAVING but before the final ORDER BY and LIMIT. This means you cannot filter on window function results in a WHERE clause — wrap the query in a CTE or subquery.

PARTITION BY divides rows into independent groups (like GROUP BY, but keeps every row). ORDER BY inside OVER defines the sort within each partition and implicitly activates a default frame. Without ORDER BY, the frame is the entire partition. With ORDER BY, the default frame is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW — which includes all peers (rows with equal ORDER BY values) in the "current row" boundary.

Frame clauses — the most misunderstood part of window functions:

  • ROWS BETWEEN N PRECEDING AND CURRENT ROW: Exactly N rows by physical position. Predictable for moving averages.
  • RANGE BETWEEN N PRECEDING AND CURRENT ROW: All rows within N units of the current ORDER BY value (peer-group aware). Required for date-based ranges like "7 days prior."
  • ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING: Full partition. Required for LAST_VALUE to work correctly — without it, LAST_VALUE returns the current row.
  • GROUPS mode (PG11+): Counts peer groups rather than rows — useful for ranked data where ties should be treated as one unit.

RANK vs DENSE_RANK vs ROW_NUMBER: rank() ties share the same rank, leaving gaps (1, 2, 2, 4). dense_rank() has no gaps (1, 2, 2, 3). row_number() always unique regardless of ties. Use row_number() for deduplication/pagination, rank() for competition-style leaderboards, dense_rank() for reporting where gaps would confuse users.

⚠️

LAST_VALUE gotcha: The default frame ends at CURRENT ROW, so LAST_VALUE returns the current row's value — not the partition's last value. Always add ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING when using LAST_VALUE or NTH_VALUE.

The WINDOW w AS (…) clause defines a named window reused across multiple functions — avoids repetition and ensures all functions use the identical window definition.

SQLWindow functions — the most powerful SQL feature
── Anatomy of a window function ─────────────────────
function_name(args) OVER (
  [PARTITION BY partition_expr]
  [ORDER BY sort_expr]
  [ROWS|RANGE|GROUPS BETWEEN frame_start AND frame_end]
)

── Ranking functions ─────────────────────────────────
SELECT
  user_id, total,
  rank()         OVER w AS rnk,         -- gaps on ties
  dense_rank()   OVER w AS drnk,        -- no gaps
  row_number()   OVER w AS rn,           -- always unique
  ntile(4)       OVER w AS quartile,    -- bucket (1-4)
  percent_rank() OVER w AS pct_rank
FROM  orders
WINDOW w AS (PARTITION BY user_id ORDER BY total DESC);

── Running totals & moving avg ───────────────────────
SELECT
  created_at::date,
  sum(total) AS daily_rev,
  sum(sum(total)) OVER (ORDER BY created_at::date)
    AS cumulative_rev,
  avg(sum(total)) OVER (
    ORDER BY created_at::date
    ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
  ) AS rolling_7d_avg
FROM   orders
GROUP BY created_at::date
ORDER BY 1;

── LAG / LEAD — access adjacent rows ─────────────────
SELECT
  user_id,
  total,
  created_at,
  lag(total, 1) OVER (PARTITION BY user_id ORDER BY created_at)
    AS prev_order_total,
  total - lag(total, 1) OVER (PARTITION BY user_id ORDER BY created_at)
    AS change_from_prev
FROM orders;

── FIRST_VALUE / LAST_VALUE / NTH_VALUE ─────────────
SELECT
  id,
  total,
  first_value(total) OVER (PARTITION BY user_id
    ORDER BY created_at
    ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
  ) AS first_order_total
FROM orders;

Indexes — Types & Strategy
B-Tree, Hash, GIN, GiST, BRIN, covering, partial, expression

Index Internals & Strategy

B-Tree is a balanced tree where leaf pages contain indexed values in sorted order, linked as a doubly-linked list. This makes both point lookups and range scans cheap. Height is typically 3–4 levels even for tables with hundreds of millions of rows — all searches are O(log n). B-Tree is the right default choice for 95% of indexes.

Multi-column index key order matters: an index on (a, b, c) supports queries filtering on (a), (a, b), or (a, b, c), but NOT on (b) or (c) alone — the leftmost prefix rule. For mixed predicate types, put equality columns first, then range columns: (status, created_at) for WHERE status = 'active' AND created_at > X.

Covering indexes (INCLUDE) store extra columns in B-Tree leaf pages without including them in the key. The planner can satisfy queries entirely from the index (Index Only Scan), skipping the heap entirely. This eliminates expensive random-access heap fetches on hot read paths. The INCLUDE columns don't affect sort order and can't be used in WHERE — they're payload.

Partial indexes index only rows matching a WHERE clause. They're smaller (faster to scan, fits in cache), cheaper to update (skip rows that don't match), and can enforce conditional uniqueness. The WHERE predicate must use immutable expressions and your queries must reference the same expression for the planner to consider the index.

Expression indexes index a computed expression rather than a raw column. The query must use the exact same expression — WHERE lower(email) = ... requires CREATE INDEX ON users(lower(email)). The expression must be immutable.

⚠️

When NOT to index: Low-cardinality columns (boolean flags, a status with 3 values — the planner may prefer a seq scan anyway), very small tables (<1000 rows), write-heavy tables where index maintenance overhead dominates. Every index slows INSERT/UPDATE/DELETE and increases VACUUM workload. Monitor pg_stat_user_indexes for indexes with idx_scan = 0.

GIN (Generalized Inverted Index) stores an inverted posting list: each element (JSONB key/value, array element, tsvector lexeme) maps to the set of row IDs containing it. Excellent for containment queries (@>, ?, @@). Slower to build and update than B-Tree due to posting list maintenance. Use gin_pending_list_limit to control insert buffering.

BRIN (Block Range Index) stores min/max values per range of pages (128 pages by default), not per row. Tiny size (~handful of KB for massive tables), near-zero insert overhead. Only useful when data has strong physical correlation with the indexed column — e.g., an append-only log table where created_at increases monotonically with physical page order.

Transactions & Concurrency
Isolation levels, locking, advisory locks, deadlocks

Concurrency Control Deep Dive

PostgreSQL implements MVCC (see Section 1) so readers never block writers. Isolation levels control what concurrent writes a transaction can observe.

  • Read Committed (default): Each statement gets a fresh snapshot. You can see data committed by other transactions between statements in the same transaction. A long-running report can see a moving target. Good enough for most OLTP but can cause non-repeatable reads within a transaction.
  • Repeatable Read: Snapshot is taken at the first statement of the transaction and held throughout. You always see the database as it was when your transaction started. PostgreSQL's implementation also prevents phantom reads (stronger than ANSI SQL requires). Use this for analytics queries requiring a consistent view.
  • Serializable (SSI): PostgreSQL uses Serializable Snapshot Isolation — detects read/write dependency cycles that would make concurrent transactions non-serializable and aborts one with a serialization failure (ERROR: could not serialize access). Applications must retry on this error. Zero blocking overhead — conflicts are detected, not prevented. Use for financial ledgers, inventory counters, and any "check-then-act" pattern.

Lock mode hierarchy (lightest to heaviest): ACCESS SHARE (SELECT) → ROW SHARE (SELECT FOR UPDATE/SHARE) → ROW EXCLUSIVE (INSERT/UPDATE/DELETE) → SHARE UPDATE EXCLUSIVE (VACUUM, CREATE INDEX CONCURRENTLY) → SHARE (CREATE INDEX non-concurrent) → ACCESS EXCLUSIVE (DROP, most ALTER TABLE). The key production insight: a queued ACCESS EXCLUSIVE blocks all subsequent queries, so even a fast DDL on a busy table causes a thundering herd of blocked connections.

Deadlock Detection

Postgres auto-detects deadlocks (default deadlock_timeout = 1s — the interval before the deadlock checker runs) and rolls back one transaction with ERROR: deadlock detected. Prevention: always acquire locks in the same consistent order across all code paths. Never hold a transaction open while waiting for user input, an HTTP call, or any external I/O.

🔴

Always order UPDATE/SELECT FOR UPDATE statements consistently across transactions. A classic deadlock: Transaction A locks row 1 then row 2; Transaction B locks row 2 then row 1. Fix: both must lock row 1 first. Use advisory locks as a higher-level mutex for cross-table workflows.

✅

FOR UPDATE SKIP LOCKED is the correct pattern for distributed job queues. Multiple workers compete for pending rows — SKIP LOCKED causes each worker to skip rows already locked by a peer, instead of blocking. Combine with LIMIT to atomically claim a batch of jobs with zero contention.

Views, CTEs & Subqueries
Materialized views, recursive CTEs, lateral subqueries

CTEs, Views & Subquery Concepts

CTE inlining (PG12+ change): In PostgreSQL 11 and earlier, every CTE was always materialized as an optimization fence — the planner could NOT push predicates through it. In PG12+, CTEs are inlined by default and the planner can optimize through them. This changes performance characteristics of existing queries on upgrade. Force materialization explicitly with WITH data AS MATERIALIZED (…) when you want guaranteed single evaluation (e.g., expensive aggregation reused twice). Force inlining with NOT MATERIALIZED.

Recursive CTEs use a "working table" algorithm: (1) execute the anchor query once, seed the working table; (2) execute the recursive term against the working table, append results to the accumulator and replace the working table with the new rows; (3) repeat until the recursive term produces no rows. The path array trick — WHERE NOT (e.id = ANY(path)) — prevents infinite loops on cyclic graphs. This is how tree traversals, graph BFS, and date-range generation work.

Materialized Views trade staleness for query speed. REFRESH MATERIALIZED VIEW takes an ACCESS EXCLUSIVE lock, blocking all reads. REFRESH MATERIALIZED VIEW CONCURRENTLY computes a diff against the existing data (requires a unique index) and applies changes with minimal locking — reads continue during refresh. Trigger refreshes from the application after significant data changes, or schedule via pg_cron.

Views are stored queries — no data stored. Simple views (single table, no aggregates/DISTINCT/LIMIT) are automatically updatable. WITH CHECK OPTION prevents inserts/updates through the view that would produce rows invisible to the view's WHERE clause — enforces the view as a row-level constraint.

💡

CTE as a readable pipeline: Chain named CTEs to build step-by-step transformations that read like a data flow. Each CTE is a named result set reusable within the query — far clearer than deeply nested subqueries. The optimizer sees them as a single query in PG12+.

SQLCTEs, recursive queries, materialized views

  -- Anchor: top-level employees
  SELECT id, name, manager_id, 0 AS depth, ARRAY[id] AS path
  FROM   employees
  WHERE  manager_id IS NULL

  WHERE  NOT (e.id = ANY(o.path))  -- cycle guard
)

FROM   org_tree
ORDER BY path;

Query Planner & EXPLAIN
Reading execution plans, statistics, planner hints

How the Query Planner Works

PostgreSQL uses a cost-based optimizer. It enumerates possible plans (within join reordering limits — geqo_threshold) and estimates the cost of each. Costs are in abstract units: seq_page_cost = 1.0 (baseline), random_page_cost = 4.0 (HDD, use 1.1 for SSD/NVMe), CPU costs are fractional. Total cost = (page fetch cost × pages) + (CPU cost × rows). The planner picks the lowest-cost plan.

Statistics drive cost estimates. Key stats in pg_stats:

  • n_distinct: Estimated distinct value count. Negative = fraction of table rows. Affects cardinality estimates for GROUP BY, joins.
  • correlation: Physical ordering correlation (-1 to 1). High correlation means heap pages are accessed nearly sequentially → index scan is efficient. Low correlation → random I/O → planner prefers Bitmap Heap Scan or Seq Scan.
  • most_common_vals / most_common_freqs: Histogram for selective predicate estimates. Stale stats → bad row count estimates → wrong plan. Run ANALYZE after large bulk loads.

Extended statistics (CREATE STATISTICS … (dependencies, ndistinct, mcv)) teach the planner about correlations between columns — e.g., city and zip_code are not independent. Without this, the planner multiplies individual selectivities and dramatically underestimates row counts for combined predicates.

Reading EXPLAIN output: Each node shows cost=startup..total rows=estimate width=bytes. With ANALYZE: actual rows and actual time. Large discrepancies between estimated and actual rows signal stale statistics or a statistics gap. The most expensive node is usually where to focus optimization. BUFFERS shows shared hit/read — reads mean disk I/O; hits mean served from shared_buffers.

⚠️

Never use planner disabling flags in production (enable_seqscan=off, enable_hashjoin=off). They're for diagnosis only. If the planner makes a wrong choice, fix the root cause: update statistics, add an index, create extended statistics, or adjust random_page_cost. Disabled flags cause fragile, hard-to-explain plan behavior.

Table Partitioning
Range, list, hash partitioning — declarative partitioning

Partitioning: When, Why & How

Declarative partitioning (PG10+) splits one logical table into multiple physical child tables. The parent is a routing shell — all data lives in partitions. The planner uses partition pruning to skip partitions whose bounds cannot satisfy the query's predicate, turning a 3-year table scan into a single-month scan — but only when the partition key appears in the WHERE clause with a constant or parameter.

Partitioning strategies:

  • RANGE: Best for time-series and temporal data. Old partitions can be DETACHed (instant, non-blocking in PG14+) then archived or dropped — far cheaper than DELETE on huge tables. New partitions must be created in advance (pg_partman automates this).
  • LIST: Best for known discrete values (country, region, tenant). Each partition maps to an explicit set of values. Enables routing queries to a single partition when filtering by that value.
  • HASH: Best for even distribution of high-cardinality keys (user_id, UUID) with no natural affinity. Prevents hot spots but offers no pruning benefit unless the exact hash value is known.

Indexes on partitioned tables: Indexes are created per-partition — there are no true global unique indexes across partitions (except when the unique constraint includes the partition key). Cross-partition uniqueness must be enforced at the application layer or via an additional lookup table.

When partitioning helps: Tables >50–100 GB where queries target a time window; easy partition-level DROP for archival; autovacuum can work per-partition in parallel; partial indexes per partition. When it hurts: Small tables (planning overhead outweighs benefit); queries with no partition key in WHERE (full fan-out across all partitions); too many partitions (1000+ slows planning); complex FK relationships (each partition needs its own FK index).

✅

Partition detach before drop: ALTER TABLE events DETACH PARTITION events_2022 CONCURRENTLY (PG14+) is near-instant and non-blocking. The detached partition becomes a standalone table — archive it to cold storage, copy it out, then DROP it without impacting the live table.

Functions & Stored Procedures
PL/pgSQL, set-returning, security definer, procedures with COMMIT

Functions & Procedures: Architecture

Volatility categories are one of the most important concepts for function performance and correctness:

  • IMMUTABLE: Same inputs → same output, no DB access, no side effects. The planner can constant-fold calls at plan time, and you can build expression indexes on IMMUTABLE functions. Example: lower(), abs(), mathematical functions.
  • STABLE: Same result within a single query/transaction, may read from the DB. The planner can call it once per query and reuse the result. Example: now(), current_user, functions reading configuration tables.
  • VOLATILE (default): Can return different results per call, may have side effects. Called once per row per reference. Example: random(), nextval(), functions that write to tables.

Language choice: LANGUAGE sql is a transparent wrapper — the planner inlines the function body and optimizes it alongside the calling query. LANGUAGE plpgsql is a fully procedural language with variables, loops, cursors, and exception handling, but is opaque to the planner (no inlining). Use SQL functions for simple expressions meant to be inlined; use PL/pgSQL for complex logic.

Functions vs Procedures (PG11+): Functions return a value and run inside the caller's transaction. Procedures (called via CALL) can execute COMMIT/ROLLBACK mid-execution — essential for long-running batch jobs that must checkpoint progress without holding one enormous transaction open for minutes.

SECURITY DEFINER functions run with the owner's privileges rather than the caller's. Useful for controlled privilege escalation (e.g., let app users call a function that accesses an admin table). Critical security requirement: always set search_path = schema, pg_temp explicitly to prevent search path injection attacks where a malicious user creates objects in a schema that shadows pg_catalog.

✅

PARALLEL SAFE/UNSAFE/RESTRICTED: Marking functions correctly enables the planner to use parallel workers. PARALLEL SAFE = can be called in parallel workers. PARALLEL RESTRICTED = only in leader process. PARALLEL UNSAFE (default) = disables parallelism for the entire query.

Triggers
Row-level, statement-level, INSTEAD OF, event triggers

Trigger Mechanics & Timing

Triggers fire on DML events (INSERT, UPDATE, DELETE, TRUNCATE) or DDL events. The combination of timing and scope gives eight distinct trigger types:

  • BEFORE ROW: Fires before each affected row is written. Can modify NEW (for INSERT/UPDATE) to alter the stored value, or return NULL to skip the row entirely. Used for: auto-setting timestamps, normalizing input, enforcing complex business rules.
  • AFTER ROW: Fires after each row is written. Cannot change the stored data but sees the committed row. Used for: audit logs, cascading updates, sending notifications. The most common production trigger type.
  • BEFORE/AFTER STATEMENT: Fires once per SQL statement regardless of rows affected (even zero rows). No OLD/NEW row variables. Use transition tables (REFERENCING NEW TABLE AS new_data) for bulk access to changed rows.
  • INSTEAD OF: Only on views. Replaces the INSERT/UPDATE/DELETE entirely. Enables updatable views with arbitrary complexity.

Trigger execution order: BEFORE triggers run before AFTER triggers. Multiple triggers on the same event/timing fire in alphabetical order by name. Plan trigger names accordingly when order matters.

OLD and NEW records: Row-level triggers receive OLD (pre-change row, NULL on INSERT) and NEW (post-change row, NULL on DELETE) as implicit variables in PL/pgSQL. TG_TABLE_NAME, TG_OP, TG_WHEN provide context about the triggering event.

⚠️

Trigger anti-patterns: Triggers create hidden side effects that make debugging and reasoning about the system hard. Cascading triggers (A fires DML that fires B that fires C) create performance nightmares and obscure execution paths. Triggers that call external services or do heavy computation block the originating transaction. Prefer explicit application logic or deferred background jobs for complex workflows. Use triggers only for tightly-scoped, database-internal concerns like audit logs and timestamp maintenance.

JSON & JSONB
Operators, path queries, aggregation, jsonpath (PG12+)

JSON vs JSONB: Architecture & Tradeoffs

json stores the raw text verbatim. It preserves key insertion order, whitespace, and duplicate keys. Every access re-parses the entire string — O(n) per query. Cannot be indexed. The only valid use case for json over jsonb is when you specifically need to preserve exact formatting or duplicate keys (extremely rare).

jsonb stores a decomposed binary format — keys are sorted, deduplicated (last write wins for duplicates), and accessed via binary search: O(log n) per key. Supports all jsonb operators. Can be indexed with GIN. Slightly larger than json for simple documents due to the binary encoding overhead, but vastly faster for read-heavy workloads. Always prefer jsonb.

When to use JSONB vs relational columns:

  • Use JSONB for truly schemaless data: user-defined fields, event/audit payloads, third-party API responses, per-row config that varies in structure.
  • Use relational columns for any field you'll filter, sort, join, or aggregate frequently. Relational columns get type-specific statistics, can have their own indexes, and the planner understands them semantically.
  • Hybrid: keep core business columns relational (user_id, status, created_at), use JSONB for extensible metadata. Never put primary keys or FK relationships inside JSONB.

GIN indexing strategies: jsonb_ops (default) indexes every key and every value — supports @>, ?, ?|, ?&. jsonb_path_ops hashes key paths to values only — supports only @> but is smaller and faster for containment queries. Choose based on your query patterns.

jsonpath (PG12+): A full XPath-like query language for navigating JSONB. Supports filters, arithmetic, and type predicates. More expressive than operator chains for deeply nested structures. @@ operator returns boolean; jsonb_path_query returns matching elements as a set.

💡

Deep update pattern: || does a shallow merge (top-level keys only). For nested updates use jsonb_set(doc, '{path,to,key}', value). PG14+ supports subscript assignment: metadata['address']['city'] = '"Mumbai"'::jsonb. Remove a key with metadata - 'key' or metadata #- '{nested,key}'.

Replication & High Availability
Streaming, logical replication, WAL, Patroni, failover

Replication Architecture Deep Dive

WAL is the backbone of both durability and replication. Every data change is written to WAL segments (16 MB files by default). Streaming replication sends these WAL bytes to standbys in real time. Logical replication decodes the WAL into row-level change events via the pgoutput (or other) decoder plugin.

Synchronous commit modes (set via synchronous_commit):

  • off: WAL written asynchronously — fastest, but up to ~1 WAL buffer (~64KB) of recent commits can be lost on crash.
  • local (default when no sync standbys): WAL flushed to local disk before commit returns.
  • remote_write: WAL received by standby (written to OS buffer) before commit returns. Fast failover but standby OS crash can lose data.
  • remote_apply: WAL applied by standby before commit returns. True zero-RPO. Adds standby apply latency to every write commit.
  • on: WAL flushed by standby (fsync'd) before commit returns. Maximum durability guarantee.
🔴

Replication slot danger: Slots prevent WAL segment deletion until the subscriber has consumed them. If a subscriber disconnects or falls behind, WAL accumulates on disk indefinitely — a disk-full crash on the primary is a real production incident. Always monitor pg_replication_slots.confirmed_flush_lsn lag. Set max_slot_wal_keep_size (PG13+) as a hard cap on WAL retention per slot.

Physical (Streaming) Replication

Binary WAL stream. Replica is exact byte-for-byte copy. Best for HA standby and read replicas. Synchronous or asynchronous.

Logical Replication

Row-level changes via publication/subscription. Can replicate specific tables across versions or to different schemas. Used for zero-downtime upgrades.

Patroni

HA framework using etcd/Consul/ZooKeeper for leader election. Auto-failover with configurable sync modes. Industry standard for production Postgres HA.

WAL Archiving (PITR)

Archive WAL segments to S3/GCS. Combined with base backups enables Point-in-Time Recovery to any moment.

Performance Tuning
Config tuning, connection pooling, parallel queries, autovacuum

Connection Overhead & Pooling

Each PostgreSQL connection spawns a dedicated OS process (5–10 MB RSS). At 200 connections, you're burning 1–2 GB just for process overhead before any query runs. With 1000+ application connections (common in microservices), direct connections will exhaust memory and trigger OS scheduling overhead.

PgBouncer pool modes — choose based on your application's usage patterns:

  • session: One server connection per client session. Equivalent to no pooling. Supports all PostgreSQL features (prepared statements, SET variables, advisory locks, LISTEN/NOTIFY). Use only for apps that maintain long-lived connections.
  • transaction: Server connection held only for the duration of a transaction block, then returned to pool. Best throughput. Incompatible with session-scoped features (prepared statements by name, SET that must persist). Standard choice for most web applications.
  • statement: Connection returned after every statement — cannot use multi-statement transactions at all. Rarely used.
💡

Parallel query: PostgreSQL can use multiple background worker processes to execute a single query (Gather/Gather Merge plan nodes). Only beneficial for large seq scans and aggregations — not index lookups. Configure with max_parallel_workers_per_gather. Each parallel worker uses its own work_mem allocation.

Autovacuum: The Hidden Engine

Autovacuum is not optional — it is critical for both correctness and performance. It performs two jobs:

  • VACUUM: Marks dead tuples (from MVCC updates/deletes) as free space for reuse. Without it, tables grow indefinitely (bloat). Also updates the visibility map for Index Only Scans and freezes old transaction IDs to prevent XID wraparound.
  • ANALYZE: Updates table statistics for the query planner. Stale stats lead to bad query plans.

Autovacuum triggers when dead tuples exceed autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor × n_live_tup. Default scale factor is 20% — on a 100M row table, that's 20M dead tuples before autovacuum fires. High-churn tables need much lower thresholds (1–5%). The autovacuum cost delay (autovacuum_vacuum_cost_delay) throttles I/O to avoid impacting production — reduce it for tables that need faster cleanup.

Table bloat builds when autovacuum can't keep up with write rate or when transactions hold old snapshots (preventing dead tuple reclamation). pg_repack rebuilds bloated tables and indexes online without ACCESS EXCLUSIVE lock.

Security & Roles

PostgreSQL Security Model

Role hierarchy: PostgreSQL uses roles for both users (roles with LOGIN) and groups (roles without LOGIN). Roles inherit privileges from parent roles by default (INHERIT attribute). You can model least-privilege access: create a read-only group role, grant it SELECT on tables, then grant the group role to individual user roles. Use SET ROLE app_readonly to explicitly switch context, or rely on INHERIT for automatic privilege inheritance.

Privilege layers from coarsest to finest:

  • Cluster: CREATEDB, CREATEROLE, REPLICATION, SUPERUSER
  • Database: CONNECT, TEMPORARY, CREATE (schema)
  • Schema: USAGE (see objects), CREATE (add objects)
  • Table: SELECT, INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER
  • Column: SELECT, INSERT, UPDATE on specific columns

Always grant minimum necessary privileges. Use ALTER DEFAULT PRIVILEGES to ensure future objects created in a schema automatically get the right grants — without this, new tables are invisible to application roles until manually granted.

Row-Level Security (RLS) is implemented as a query rewrite rule — every SELECT/INSERT/UPDATE/DELETE on an RLS-enabled table has the policy's USING/WITH CHECK expression invisibly appended. The application writes SELECT * FROM orders and only sees its own rows. Set application context via SET LOCAL app.tenant_id = '42' at the start of each transaction (or connection for PgBouncer session mode).

🔴

SECURITY DEFINER risk: The function runs with owner privileges, bypassing the caller's permission model. An attacker with EXECUTE permission can potentially exploit it to access tables they shouldn't. Always: (1) set search_path = public, pg_temp to prevent schema injection, (2) validate all inputs, (3) grant EXECUTE only to specific roles. Audit all SECURITY DEFINER functions regularly.

SQLProduction security setup
── Role-based access control ─────────────────────────
CREATE ROLE app_readonly;
GRANT CONNECT ON DATABASE mydb TO app_readonly;
GRANT USAGE ON SCHEMA public TO app_readonly;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO app_readonly;
ALTER DEFAULT PRIVILEGES IN SCHEMA public
  GRANT SELECT ON TABLES TO app_readonly;

CREATE ROLE app_user LOGIN PASSWORD '...' IN ROLE app_readonly;

── Row-Level Security (RLS) ──────────────────────────
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;

-- Users can only see their own orders

  USING (user_id = current_setting('app.current_user_id')::bigint);

-- Set at connection time:
SET app.current_user_id = '42';
SELECT * FROM orders;  -- only returns user 42's orders

-- Bypass RLS for service role
ALTER TABLE orders FORCE ROW LEVEL SECURITY;
CREATE ROLE service_role BYPASSRLS;

── Column-level privileges ───────────────────────────

GRANT SELECT (id, email, username) ON users TO app_user;

── SECURITY DEFINER function (run as owner) ──────────

RETURNS TABLE(id bigint, email text)
LANGUAGE sql SECURITY DEFINER
SET search_path = public  -- prevent search_path injection!
AS $$ SELECT id, email FROM users $$;

Extensions: How They Work

PostgreSQL extensions package SQL objects (functions, types, operators, indexes), C code, and configuration together. CREATE EXTENSION installs them into the current database. Extensions are schema-namespaced and versionable. Key extensions every senior engineer should know:

  • pg_stat_statements: The most important production monitoring extension. Tracks execution stats per query fingerprint (normalized, parameter-stripped). Use it to identify top consumers by total time, mean time, or I/O. Essential for query performance analysis.
  • pg_trgm: Trigram-based similarity. A trigram is a set of 3 consecutive characters. The extension creates GIN/GiST indexes on these trigrams, enabling fast LIKE '%substring%' and fuzzy (similarity()) searches without a full-text search stack.
  • pgvector: Adds a vector(n) type and approximate nearest-neighbor indexes (IVFFLAT — inverted file with flat quantization; HNSW — hierarchical navigable small world graph, faster but more memory). Used for semantic similarity search over ML embeddings. HNSW has better query performance; IVFFLAT builds faster.

Backup Strategies & PITR Concepts

Logical backups (pg_dump) export data as SQL or binary format. Portable across major versions, selective (table/schema-level), compressible. Slow for large databases (must read every row), and require a running, accessible cluster. The -Fc (custom format) with -j N (N parallel workers) is the standard approach: parallel dump reduces wall time; pg_restore -j parallelizes restore.

Physical backups (pg_basebackup, pgBackRest) copy the entire data directory at the filesystem level. Much faster for large databases, required for PITR, but tied to the same major PostgreSQL version.

Point-in-Time Recovery (PITR) is the combination of a base backup + continuous WAL archiving. Recovery process:

  1. Restore the base backup to the data directory
  2. Configure restore_command (copies WAL segments from archive to the recovery directory)
  3. Set recovery_target_time (or LSN, or transaction ID)
  4. Start PostgreSQL — it replays WAL segments from the archive until it hits the target, then promotes

PITR lets you recover from logical disasters (accidental DROP TABLE, mass bad update) to within seconds of any point in your WAL retention window.

RPO vs RTO: Recovery Point Objective — how much data can you afford to lose? Async replication: RPO = seconds. Synchronous: RPO = zero. Recovery Time Objective — how fast must you recover? PITR with pgBackRest parallel restore typically achieves RTO in minutes for most workloads. Test your RTO regularly — it's always longer than you estimate.

✅

pgBackRest is the production standard: parallel backup/restore, incremental/differential backups, built-in S3/GCS/Azure support, retention management, and a --verify command to confirm backup integrity without a full restore. Replaces both WAL-E and custom archiving scripts.

BASH + SQLBackup & recovery commands
# ── Logical backup (pg_dump) ──────────────────────────
pg_dump -Fc -Z9 -j4 mydb > mydb.dump         # custom format, compressed, 4 parallel jobs
pg_dump -Fd -j8 -f /backups/mydb mydb         # directory format for parallel restore
pg_dump --table=orders mydb > orders.sql      # single table

# Restore
pg_restore -Fc -j4 -d mydb_restore mydb.dump
psql -d newdb < schema.sql

# ── Physical backup (streaming) ───────────────────────
pg_basebackup -h primary -U replicator \
  -D /var/lib/postgresql/backup \
  -Ft -z -P -Xs              # tar, gzip, progress, stream WAL

# ── pgBackRest (production tool) ─────────────────────
pgbackrest --stanza=mydb backup --type=full
pgbackrest --stanza=mydb backup --type=incr
pgbackrest --stanza=mydb restore \
  --target="2024-06-15 14:30:00" \
  --target-action=promote

── PITR via recovery.conf (PG11 and earlier) ─────────
-- In postgresql.conf (PG12+):
restore_command = 'cp /wal_archive/%f %p'
recovery_target_time = '2024-06-15 14:30:00 UTC'
recovery_target_action = 'promote'


── Test your backups! ────────────────────────────────
-- Restore to a separate instance, verify data integrity
SELECT count(*) FROM orders;
SELECT max(created_at) FROM orders;

── Monitor WAL archiving ─────────────────────────────

       last_archived_time, last_failed_wal
FROM   pg_stat_archiver;
🔴

An untested backup is not a backup. Always run scheduled restore drills on a separate environment. Verify row counts and data integrity after every restore test.
