01
Fundamentals & Why OAuth2
The problem OAuth2 solves, what it is and isn't, RFC 6749 basics

The Problem OAuth2 Solves

Before OAuth2, delegated access meant sharing passwords. If you wanted a third-party app to read your Gmail, you gave it your Google password. The app now had full, permanent, irrevocable access to everything — and you couldn't take it back without changing your password, which affected all other apps too.

OAuth2 (RFC 6749) is an authorization framework — not an authentication protocol — that enables an application to obtain limited access to a user's account on another service, without sharing credentials. It does this by issuing short-lived, scope-limited tokens on behalf of the user after explicit consent.

💡

OAuth2 is NOT authentication. It answers "what can this app do?" not "who is this user?" Authentication (verifying identity) is layered on top via OpenID Connect (OIDC). This distinction is the #1 interview point — OAuth2 without OIDC tells you nothing about who the user is, only that they consented.

What OAuth2 Is and Isn't

OAuth2 IS

An authorization framework (RFC 6749). A delegation protocol. A standard for issuing limited-scope access tokens. A way for third-party apps to act on a user's behalf. A mechanism for machine-to-machine API access.

OAuth2 is NOT

An authentication protocol. A definition of token format (that's JWT). A security protocol by itself (needs PKCE, state, nonce). A user management system. A substitute for proper API security design.

OAuth2 vs OAuth1

OAuth1 required cryptographic signing of every request (HMAC-SHA1) — complex to implement and nearly impossible to use without a library. OAuth2 relies entirely on HTTPS for transport security, removes request signing, and introduces bearer tokens. Much simpler but requires TLS everywhere. OAuth1 is effectively dead; all modern systems use OAuth2.

Core Token Types

TokenPurposeLifetimeFormat
Access TokenPresented to resource servers to access protected APIsShort (minutes–hours)JWT or opaque
Refresh TokenObtain new access tokens without re-authenticatingLong (hours–days)Opaque (mostly)
ID TokenProve identity of the user (OIDC only)Short (minutes)Always JWT
Authorization CodeSingle-use, short-lived code exchanged for tokensSeconds (60s max)Opaque string
⚠️

Bearer tokens are dangerous if leaked. Anyone who possesses an access token can use it — there's no signature verification by the caller. This is why short expiry, HTTPS everywhere, and token binding (DPoP, mTLS) exist. "Bearer" means "whoever holds it can use it."

The Trust Model

OAuth2 works because the Authorization Server (AS) is the single trusted issuer. Resource servers trust the AS to issue valid tokens. Clients trust the AS to enforce user consent. The user trusts the AS (Okta, Google, etc.) as their identity provider. The AS is the security anchor of the entire system — its compromise breaks everything.

Roles, Actors & Terminology
Resource Owner, Client, Authorization Server, Resource Server — and how they interact

The Four Roles (RFC 6749 §1.1)

Resource Owner (RO)

The entity that owns the protected resource — usually the end user. Can grant or deny access to their data. In machine-to-machine flows, the resource owner may be the system itself.

Client

The application requesting access (web app, mobile app, CLI, microservice). Does NOT see the user's credentials. Classified as confidential (can keep a secret) or public (cannot keep a secret — SPA, mobile app).

Authorization Server (AS)

Issues tokens after authenticating the user and obtaining consent. Validates client identity, enforces scopes. Examples: Okta, Auth0, Keycloak, Google, AWS Cognito. The AS is the trust anchor.

Resource Server (RS)

Hosts the protected APIs. Validates access tokens (locally via JWT signature, or via introspection). Enforces scope-based authorization. Often the AS and RS are different services.

Confidential vs Public Clients

This distinction drives which flows and security features are available:

PropertyConfidential ClientPublic Client

PKCE required?Recommended (RFC 9700)Mandatory
💡

RFC 9700 (OAuth 2.1 draft) makes PKCE mandatory for ALL clients — even confidential ones — and removes the implicit grant and ROPC grant entirely. While still a draft, most modern AS implementations follow these recommendations. Interview tip: mention OAuth 2.1 to signal currency.

Client Authentication Methods

How a confidential client proves its identity to the token endpoint:

  • client_secret_basic: HTTP Basic Auth header with base64(client_id:client_secret). Simple but the secret travels in every request.
  • client_secret_post: client_id and client_secret in POST body. Slightly worse than basic (body logging more common).
  • client_secret_jwt: Client generates a JWT signed with the shared secret. Time-limited, replay-resistant. Better than raw secret transmission.
  • private_key_jwt: Client signs a JWT with its private key; AS verifies with client's registered public key. Most secure — secret never transmitted. Used in FAPI.
  • tls_client_auth / self_signed_tls_client_auth: Mutual TLS — client presents a certificate. Used in banking/FAPI environments.

Why Implicit Grant Was Deprecated

Implicit returned the access token directly in the URL fragment (#access_token=…) after the redirect — no code exchange step. This was designed for SPAs before CORS was widely supported. Problems:

  • Token in URL fragment appears in browser history, referrer headers, server logs, and proxy logs
  • No way to authenticate the client — any app could impersonate the client_id
  • Cannot issue refresh tokens (tokens in fragments are tab-local)
  • Open to token injection attacks — attacker can inject their token into your app's redirect

Auth Code + PKCE solves all of these by keeping the token exchange server-side and authenticating via the PKCE code_verifier.

Why ROPC (Resource Owner Password Credentials) Was Deprecated

ROPC had the client collect the user's username and password directly and send them to the AS. This defeats the entire purpose of OAuth2 — the user's credentials are exposed to the client, which might be a third-party app. It also prevents multi-factor authentication and social login. Modern guidance: never use ROPC; use the Authorization Code flow even for first-party apps.

Device Authorization Grant (RFC 8628)

For devices with limited input (Smart TVs, IoT, CLI tools). The device polls the token endpoint while displaying a user code; the user visits a verification URL on a separate device (phone/laptop) and approves.

Device → POST /device_authorization → AS
AS → { device_code, user_code, verification_uri, interval }
Device displays: "Visit example.okta.com/activate, enter code BDFH-JKQR"
Device → polls POST /token (device_code) every interval → AS
User visits URL on phone, authenticates, approves
AS → { access_token, refresh_token } on next poll

Authorization Code + PKCE Flow
Step-by-step mechanics, state, nonce, code_verifier — the recommended flow for all user-facing clients

Full Authorization Code + PKCE Flow

Step 1 — Client generates PKCE parameters
code_verifier = cryptographically random 43–128 char string
code_challenge = BASE64URL(SHA256(code_verifier)) ← S256 method
state = cryptographically random string ← CSRF protection

Step 2 — Redirect to Authorization Endpoint
Browser → GET /authorize?
  response_type=code
  client_id=my-app
  redirect_uri=https://app.example.com/callback
  scope=openid profile email
  state=abc123xyz
  code_challenge=E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM
  code_challenge_method=S256

Step 3 — User authenticates & consents at AS
AS shows login page → user enters credentials → MFA → consent screen

Step 4 — AS redirects back with authorization code
AS → 302 redirect → https://app.example.com/callback?code=AUTH_CODE&state=abc123xyz
Client MUST verify state matches what was sent (CSRF check)

Step 5 — Exchange code for tokens (back-channel)
Server → POST /token → AS
  grant_type=authorization_code
  code=AUTH_CODE
  redirect_uri=https://app.example.com/callback
  code_verifier=(original random string) ← AS hashes and compares to challenge
  client_id=my-app [+ client_secret for confidential clients]

Step 6 — AS returns tokens
{ access_token, token_type: "Bearer", expires_in, refresh_token, id_token }

PKCE — Why It Works

PKCE (Proof Key for Code Exchange, RFC 7636) prevents authorization code interception attacks. Scenario: on mobile, a malicious app registers the same custom URL scheme as your app and steals the authorization code from the redirect. Without PKCE, the attacker can exchange that code for tokens. With PKCE, they can't — because they don't have the code_verifier that was generated in your app's memory and sent with the token exchange.

The AS stores the code_challenge (hash of verifier) alongside the issued code. When the token exchange arrives with code_verifier, the AS computes SHA256(code_verifier) and compares it — only the original requester can produce the matching verifier.

✅

Always use S256 (SHA-256) as code_challenge_method, never plain. The plain method sends the verifier directly, defeating the purpose — an interceptor gets both the code AND the verifier.

State Parameter — CSRF Protection

The state parameter binds the authorization request to the user's session. Before redirecting to the AS, store the state value in the session (or a signed cookie). After the callback, verify the returned state matches. This prevents CSRF attacks where an attacker tricks a user's browser into completing an OAuth flow initiated by the attacker.

Nonce — Replay Protection for ID Tokens

The nonce parameter is included in the authorization request and must appear in the returned ID Token's nonce claim. The client verifies this after receiving the ID Token. This prevents replay attacks where an attacker captures an ID Token and replays it to another session.

HTTPAuthorization request with all security parameters
GET /oauth2/v1/authorize HTTP/1.1
Host: dev-12345.okta.com

response_type=code
&client_id=0oa1b2c3d4e5f6g7h8i9
&redirect_uri=https%3A%2F%2Fapp.example.com%2Fcallback
&scope=openid+profile+email+offline_access
&state=J7CvSx9mNqR8pZkL4wTyH2oB        ← CSRF token (32 random bytes)
&nonce=aP9kX3mQ7nZ1eW8vF4tY5sL         ← Replay protection for ID token

05
Client Credentials — Machine-to-Machine
Service-to-service auth, no user involved, scopes as permissions

Client Credentials Flow

The simplest OAuth2 flow — no user, no browser redirect. The client authenticates directly with the AS using its own credentials and receives an access token representing the client itself (not any user). Used for: service-to-service API calls, background jobs, daemons, microservice-to-microservice communication.

Service A → POST /token → AS
  grant_type=client_credentials
  client_id=service-a-client
  client_secret=s3cr3t ← or private_key_jwt for higher security
  scope=inventory:read orders:write

AS → { access_token, token_type, expires_in, scope }
Note: NO refresh_token — just get a new one when this expires

Service A → GET /api/inventory → Service B (RS)
  Authorization: Bearer <access_token>

Token Caching for Client Credentials

Client credentials tokens have no user session — they can and should be cached for their full lifetime. Fetching a new token on every API call is wasteful and adds latency. Cache the token until expires_in - buffer (typically subtract 30–60 seconds as buffer for clock skew).

JavaToken cache for client credentials (Spring)
@Component
public class ClientCredentialsTokenProvider {

    private final OAuth2AuthorizedClientManager clientManager;
    private volatile OAuth2AccessToken cachedToken;

    public String getAccessToken() {
        if (isTokenValid()) return cachedToken.getTokenValue();

        OAuth2AuthorizeRequest request = OAuth2AuthorizeRequest
            .withClientRegistrationId("okta-m2m")
            .principal("service-account")
            .build();

        OAuth2AuthorizedClient client = clientManager.authorize(request);
        cachedToken = client.getAccessToken();
        return cachedToken.getTokenValue();
    }

    private boolean isTokenValid() {
        if (cachedToken == null) return false;
        Instant expiry = cachedToken.getExpiresAt();
        return expiry != null &&
               expiry.isAfter(Instant.now().plusSeconds(60)); // 60s buffer
    }
}

Scopes in Client Credentials

In client credentials flow, scopes represent the permissions of the service itself — not delegated user permissions. Define them to express what APIs the service can call. Okta supports custom scopes on API authorization servers. A good design uses verb-noun scopes: inventory:read, orders:write, payments:process. Validate these on the resource server.

⚠️

Rotate client secrets regularly. A leaked client secret in a client credentials flow gives full API access with no user to be suspicious. Use private_key_jwt or mTLS for high-security services — no secret travels over the wire. Store secrets in a vault (HashiCorp Vault, AWS Secrets Manager), not in environment variables or config files.

JWT Deep Dive
Structure, signing algorithms, validation, JWKS, attack vectors

JWT Structure

A JWT (JSON Web Token, RFC 7519) is three Base64URL-encoded JSON objects separated by dots: HEADER.PAYLOAD.SIGNATURE. None of it is encrypted by default (that's JWE) — it's signed, not secret. Never put sensitive data in a JWT payload unless using JWE.

JWTDecoded JWT structure
── HEADER (algorithm + token type) ──────────────────
{
  "alg": "RS256",        // Signing algorithm
  "typ": "JWT",          // Token type
  "kid": "abc123"        // Key ID — used to find the right key in JWKS
}

── PAYLOAD (claims) ──────────────────────────────────
{
  "iss": "https://dev-123.okta.com/oauth2/default",  // Issuer
  "sub": "00u1a2b3c4d5e6f7",       // Subject (user ID)
  "aud": "https://api.example.com", // Audience (MUST match RS)
  "iat": 1718000000,              // Issued At (Unix timestamp)
  "exp": 1718003600,              // Expiration (iat + 3600s)
  "nbf": 1718000000,              // Not Before
  "jti": "k9f2mX3nP7qR",          // JWT ID — unique per token (replay prevention)
  "scope": "openid profile email",
  "scp": ["openid", "profile", "email"],  // Okta uses array
  "groups": ["ROLE_ADMIN", "ROLE_USER"],   // Custom claim from Okta
  "email": "alice@example.com"
}

── SIGNATURE ─────────────────────────────────────────
RSASHA256(
  base64url(header) + "." + base64url(payload),
  privateKey     ← AS signs with private key
)                ← RS verifies with AS's public key (from JWKS)

Signing Algorithms

AlgorithmTypeKeyUse CaseNotes
RS256AsymmetricRSA 2048+Most common for AS-issued tokensAS signs with private key; anyone can verify with public key (JWKS)
RS384/RS512AsymmetricRSA 3072/4096Higher security requirementsSlower, larger signatures
ES256AsymmetricECDSA P-256Modern, compact tokensSmaller signatures than RSA, faster verification
PS256AsymmetricRSA-PSSFAPI, high-securityProbabilistic, more secure than PKCS1v15
HS256SymmetricShared secretInternal services onlyNEVER for AS-issued tokens — secret must be shared with every RS
🔴

Never accept "alg: none". A critical JWT vulnerability: set alg=none in the header and strip the signature — some libraries accept this if not explicitly configured to reject it. Always whitelist accepted algorithms explicitly. Also never accept HS256 when RS256 is expected — an attacker could take an RS256 public key, use it as an HS256 secret, and forge tokens.

Complete JWT Validation Checklist

Resource servers MUST validate every incoming JWT on every request:

  1. Signature: Verify using the public key fetched from the AS's JWKS endpoint, matched by kid header claim
  2. Algorithm: Confirm alg is in your allowed list (never none, never unexpected algorithm)
  3. Expiry (exp): Reject if current time ≥ exp (allow small clock skew, e.g., 5 seconds)
  4. Not Before (nbf): Reject if current time < nbf
  5. Issuer (iss): Must exactly match your expected AS URL
  6. Audience (aud): Must contain your resource server's identifier
  7. Token Type (typ): For access tokens, should be "at+JWT" (RFC 9068) or "JWT"

JWKS — JSON Web Key Set

The AS publishes its public keys at a /.well-known/jwks.json endpoint. Resource servers fetch these keys to verify JWT signatures. Keys have a kid (Key ID) that matches the JWT header's kid — this tells the RS exactly which key to use for verification.

Cache JWKS with a reasonable TTL (5–60 minutes). When you receive a JWT with an unknown kid, refresh the JWKS once (the AS may have rotated keys). If still not found, reject the token. Spring Security handles JWKS caching automatically via NimbusJwtDecoder.

JSONJWKS endpoint response
{
  "keys": [
    {
      "kty": "RSA",           // Key type
      "alg": "RS256",        // Algorithm
      "use": "sig",          // Usage: sig (signing) or enc (encryption)
      "kid": "abc123",       // Key ID — match against JWT header
      "n": "sj8qL...",       // RSA modulus (base64url)
      "e": "AQAB",           // RSA exponent
      "x5c": ["MIICpD..."]  // X.509 certificate chain (optional)
    },
    {
      "kid": "xyz789",       // Previous key (kept during rotation window)
      "kty": "EC",
      "alg": "ES256",
      "crv": "P-256",
      "x": "f83OJ3D2x...",
      "y": "x_FEzRu9m..."
    }
  ]
}

OpenID Connect (OIDC)
Identity layer on OAuth2 — ID tokens, UserInfo, discovery, claims

OIDC = OAuth2 + Identity Layer

OpenID Connect (OIDC) is a thin identity layer built on top of OAuth2. It adds:

  • ID Token: A JWT containing claims about the authenticated user, returned alongside the access token
  • UserInfo Endpoint: An API that returns user profile claims using the access token
  • Standard Claims: A defined set of user attributes (sub, name, email, picture, etc.)
  • Discovery: /.well-known/openid-configuration — machine-readable AS capabilities
  • Dynamic Client Registration (RFC 7591): Register clients programmatically

To trigger OIDC, include openid in the scope. The AS then issues an ID Token alongside the access token.

🔴

Never send an ID token to your API. The ID token is meant for the client application to verify identity — it's not an access credential for resource servers. APIs should only receive access tokens. This is a common mistake in poorly designed OAuth integrations.

UserInfo Endpoint

The UserInfo endpoint returns claims about the authenticated user based on the scopes granted. Use it when claims are too large to embed in the access token, or when you need fresh data. Protected by the access token (Bearer header). Response is a JSON object or a JWT (if userinfo_signed_response_alg is configured).

Token Lifecycle — Refresh, Rotation & Revocation
Refresh token mechanics, silent renewal, rotation strategies, revocation (RFC 7009)

Access Token Expiry & Silent Renewal

Access tokens are intentionally short-lived (minutes to hours). When an access token expires, the client uses its refresh token to get a new access token without asking the user to log in again. This is "silent renewal" — transparent to the user. The refresh token itself has a longer lifetime (hours to days) and is typically opaque (not a JWT) so it can be revoked server-side.

Client → POST /token → AS
  grant_type=refresh_token
  refresh_token=<opaque refresh token>
  client_id=my-app [+ client_secret for confidential clients]

AS → { access_token, expires_in, refresh_token (new, if rotation enabled) }

Refresh Token Rotation

With rotation, every refresh token use issues a new refresh token and invalidates the old one. This enables detection of refresh token theft — if an attacker steals and uses a refresh token, the legitimate client's next use will fail (old token rejected). The AS should detect this reuse and revoke the entire token family (all tokens issued from the same original grant).

StrategyBehaviorWhen to Use
No RotationSame refresh token reused until expiryConfidential clients in controlled environments only
Rotation without Reuse DetectionNew token each use, old invalidatedPublic clients — minimum baseline
Rotation + Reuse DetectionReuse of old token triggers family revocationAll public clients — recommended standard
Absolute LifetimeRefresh token expires regardless of activitySecurity-sensitive applications (banking)
Idle LifetimeExpires if not used within N daysConsumer apps — balance UX vs security
⚠️

Refresh token reuse detection race condition: In high-concurrency scenarios (multiple browser tabs refreshing simultaneously), legitimate clients can trigger reuse detection. Implement a short grace period (a few seconds) or use a distributed lock before revoking the family. Okta's token rotation handles this with a reuse window.

Token Revocation (RFC 7009)

Revocation allows invalidating a token before its natural expiry. Essential for logout, compromised credential handling, and permission changes. The client POSTs the token to the revocation endpoint. For opaque tokens, the AS marks it invalid immediately. For JWTs, revocation requires either a token blocklist (denylist) or short expiry as the fallback.

HTTPRevocation request (RFC 7009)
POST /oauth2/v1/revoke HTTP/1.1
Host: dev-123.okta.com
Content-Type: application/x-www-form-urlencoded
Authorization: Basic base64(client_id:client_secret)

token=<refresh_token_or_access_token>
&token_type_hint=refresh_token   ← hint for AS performance, not mandatory

Response: 200 OK (even if token was already invalid — prevents oracle attacks)

Token Introspection (RFC 7662)

Introspection allows a resource server to validate an opaque token by asking the AS. The AS returns the token's metadata: whether it's active, its claims, expiry, and scope. More expensive than JWT local validation (requires a network call per request) but necessary for opaque tokens. Use caching with a short TTL to reduce load on the AS.

HTTPToken introspection (RFC 7662)
POST /oauth2/v1/introspect HTTP/1.1
Host: dev-123.okta.com
Authorization: Basic base64(rs_client_id:rs_client_secret)

token=<opaque_access_token>

Response:
{
  "active": true,
  "sub": "00u1a2b3",
  "scope": "openid profile email",
  "client_id": "my-app",
  "exp": 1718003600,
  "iat": 1718000000,
  "iss": "https://dev-123.okta.com/oauth2/default"
}

Logout — Front-Channel vs Back-Channel

RP-Initiated Logout (OIDC): The client redirects the user to the AS's end_session_endpoint with the id_token_hint. The AS logs the user out and redirects back to post_logout_redirect_uri. Clears the AS session.

Back-Channel Logout (OIDC): The AS sends a signed logout token (JWT) directly to each client's registered backchannel_logout_uri when a session ends (even from another client). Enables true SSO logout across all client applications without browser-mediated redirects. More reliable than front-channel.

09
Scopes, Claims & Audience Validation
Scope design, claim mapping, audience binding, resource indicators (RFC 8707)

Scopes — What They Are and Aren't

Scopes are strings the client requests that represent delegated permissions. They appear in both the authorization request and the issued access token. Important distinction: scopes are requested by the client, but the AS enforces them — the AS may grant fewer scopes than requested, and the user's consent matters.

Scopes are NOT fine-grained authorization. They answer "is this client allowed to do X in general?" not "can this user do X to this specific resource?" Fine-grained authorization (can user A delete document B?) is the resource server's responsibility, using claims from the token combined with application-level rules.

Scope Design Patterns

Verb-Noun Scopes

Most readable. orders:read, orders:write, payments:process, users:admin. Granular, composable, maps to API operations. Recommended for custom APIs.

Resource-Based Scopes

api://myapp/Order.Read, api://myapp/User.Admin (Azure AD style). Namespaced to prevent collisions across services. Useful in large orgs.

💡

Define the minimum set of scopes needed (principle of least privilege). Don't create mega-scopes like admin:everything. Token claims should carry enough information for authorization decisions — scopes gate the API category, claims inside the token carry the user's specific attributes and roles.

Audience (aud) — Token Binding

The aud (audience) claim binds an access token to a specific resource server. A token issued for API A should be rejected by API B. Resource servers MUST validate that the aud claim contains their own identifier. Without audience validation, a token stolen from one API can be replayed to any other API that trusts the same AS.

Resource Indicators (RFC 8707)

In a multi-resource environment, a client requests scopes for a specific resource using the resource parameter. The AS issues a token with that resource's identifier as the aud. This prevents tokens from being usable across resources even if they share the same scope name.

HTTPResource indicator in authorization request
GET /authorize?
  response_type=code
  &client_id=my-app
  &scope=openid orders:read
  &resource=https://orders-api.example.com   ← RFC 8707
  &resource=https://inventory-api.example.com  ← multiple resources

Resulting access token aud:
{
  "aud": ["https://orders-api.example.com", "https://inventory-api.example.com"],
  "scope": "orders:read"
}

Claims-Based Authorization

Beyond scopes, tokens carry claims that resource servers use for authorization decisions. Common patterns:

  • Roles/Groups: "groups": ["ROLE_ADMIN", "ROLE_USER"] — map to Spring Security authorities
  • Tenant ID: "tid": "acme-corp" — multi-tenant data isolation
  • Custom attributes: "subscription_tier": "pro", "department": "engineering"
  • Delegated subject: "act": {"sub": "service-a"} — RFC 8693 token exchange indicator

Open Redirect — The Nastiest Misconfiguration

If the AS accepts wildcard redirect URIs (e.g., https://example.com/*), an attacker can craft an authorization request with redirect_uri=https://example.com/attacker-page. After the user consents, the AS sends the authorization code to the attacker's URL. They exchange it for tokens.

Mitigation: Always register exact redirect URIs. No wildcards. No subdomain patterns. The AS must do exact string matching, not prefix matching. This is also why Okta enforces exact URI matching by default.

Mix-Up Attack

In a multi-AS environment (a client configured for both Google and Okta), an attacker intercepts the request to Google and substitutes Okta's authorization endpoint. The user authenticates with Okta, gets a code. The client thinks it's a Google code and sends it to Google's token endpoint — which fails, but the attacker intercepts the request and gets the Okta code.

Mitigation: The AS must include an iss parameter in the authorization response (RFC 9207). The client must verify this matches the expected AS before proceeding with the token exchange.

🔴

Never log access tokens or authorization codes. They are credentials. Even logging the first/last few characters can help attackers narrow down brute-force attempts. Use structured logging that explicitly masks Authorization headers. Audit your log pipelines for token leakage.

A Spring Boot resource server is an API that accepts Bearer tokens. Spring Security intercepts every request, extracts the token from the Authorization: Bearer header, validates it (signature, expiry, issuer, audience), and populates the SecurityContext with the authenticated principal. @Configuration
@EnableWebSecurity
@EnableMethodSecurity   // enables @PreAuthorize, @PostAuthorize
public class SecurityConfig {

    @Bean
    public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
        http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/actuator/health", "/api/public/**").permitAll()
                .requestMatchers("/api/admin/**").hasAuthority("SCOPE_admin:read")
                .anyRequest().authenticated()
            )
            .oauth2ResourceServer(oauth2 -> oauth2
                .jwt(jwt -> jwt
                    .jwtAuthenticationConverter(jwtAuthenticationConverter())
                )
            )
            // Resource servers are stateless — disable session and CSRF
            .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .csrf(csrf -> csrf.disable());

        return http.build();
    }

    @Bean
    public JwtAuthenticationConverter jwtAuthenticationConverter() {
        JwtGrantedAuthoritiesConverter scopeConverter = new JwtGrantedAuthoritiesConverter();
        scopeConverter.setAuthorityPrefix("SCOPE_");         // SCOPE_openid, SCOPE_email
        scopeConverter.setAuthoritiesClaimName("scp");       // Okta uses "scp" array claim

        JwtAuthenticationConverter converter = new JwtAuthenticationConverter();
        converter.setJwtGrantedAuthoritiesConverter(scopeConverter);
        return converter;
    }

    // Optional: customize JwtDecoder for extra validation
    @Bean
    public JwtDecoder jwtDecoder(OAuth2ResourceServerProperties properties) {
        NimbusJwtDecoder decoder = NimbusJwtDecoder
            .withJwkSetUri(properties.getJwt().getJwkSetUri())
            .build();

        OAuth2TokenValidator<Jwt> withIssuer =
            JwtValidators.createDefaultWithIssuer(properties.getJwt().getIssuerUri());
        OAuth2TokenValidator<Jwt> withAudience = new JwtClaimValidator<>(
            "aud", aud -> aud.contains("https://api.example.com"));

        decoder.setJwtValidator(new DelegatingOAuth2TokenValidator<>(
            withIssuer, withAudience));
        return decoder;
    }
}

Custom Claims & Role-Based Access

How Okta Groups Become Spring Security Roles

The pipeline: Okta groups → configured as a custom claim in the Custom AS → appear in JWT payload as "groups": ["ADMIN", "USER"] → Spring Security's JwtAuthenticationConverter extracts them → converted to GrantedAuthority objects with a prefix (e.g., ROLE_ADMIN) → available in @PreAuthorize and hasRole() checks.

JavaCustom JwtAuthenticationConverter — groups + scopes as authorities
@Component
public class OktaJwtAuthenticationConverter
        implements Converter<Jwt, AbstractAuthenticationToken> {

    @Override
    public AbstractAuthenticationToken convert(Jwt jwt) {
        Collection<GrantedAuthority> authorities = new ArrayList<>();

        // 1. Extract scopes → SCOPE_ prefix
        List<String> scopes = jwt.getClaimAsStringList("scp"); // Okta: "scp" not "scope"
        if (scopes != null) {
            scopes.stream()
                .map(s -> new SimpleGrantedAuthority("SCOPE_" + s))
                .forEach(authorities::add);
        }

        // 2. Extract Okta groups → ROLE_ prefix
        List<String> groups = jwt.getClaimAsStringList("groups");
        if (groups != null) {
            groups.stream()
                .map(g -> new SimpleGrantedAuthority("ROLE_" + g))
                .forEach(authorities::add);
        }

        return new JwtAuthenticationToken(jwt, authorities);
    }
}

// Register it in SecurityConfig:
.oauth2ResourceServer(oauth2 -> oauth2
    .jwt(jwt -> jwt.jwtAuthenticationConverter(new OktaJwtAuthenticationConverter()))
)

Microservices — JWT Propagation & Token Exchange
Token relay, WebClient with OAuth2, Token Exchange (RFC 8693), service identity

Token Propagation Patterns

In a microservices architecture, when Service A calls Service B on behalf of a user, it must pass the user's identity. Three main patterns:

Token Relay (Pass-Through)

Service A forwards the incoming user access token to Service B. Simple. Service B sees the original user. Risk: a compromised Service A gets the user's full token. Works well for trusted internal services.

Client Credentials + User Context in Headers

Service A uses its own M2M token to call Service B, but passes the user's sub/claims as a custom header. Service B trusts Service A's identity and the header. Requires careful input validation on the header.

Token Exchange (RFC 8693)

Service A exchanges the user's token at the AS for a new token with reduced scope or different audience. Produces an actor/subject chain. Most secure and auditable. Full standard impersonation and delegation support.

JavaWebClient with automatic token relay (Spring Security)
@Configuration
public class WebClientConfig {

    @Bean
    public WebClient downstreamWebClient(
            OAuth2AuthorizedClientManager authorizedClientManager) {

        ServletOAuth2AuthorizedClientExchangeFilterFunction oauth2 =
            new ServletOAuth2AuthorizedClientExchangeFilterFunction(authorizedClientManager);

        // Relay the current user's access token to downstream APIs
        oauth2.setDefaultOAuth2AuthorizedClient(true);

        return WebClient.builder()
            .filter(oauth2)
            .baseUrl("https://orders-api.internal")
            .build();
    }

    @Bean
    public OAuth2AuthorizedClientManager authorizedClientManager(
            ClientRegistrationRepository clientRegistrationRepository,
            OAuth2AuthorizedClientRepository authorizedClientRepository) {

        DefaultOAuth2AuthorizedClientManager manager =
            new DefaultOAuth2AuthorizedClientManager(
                clientRegistrationRepository, authorizedClientRepository);

        // Auto-refresh expired access tokens using refresh token
        manager.setAuthorizedClientProvider(
            OAuth2AuthorizedClientProviderBuilder.builder()
                .authorizationCode()
                .refreshToken()
                .clientCredentials()
                .build()
        );
        return manager;
    }
}

Service-to-Service Identity Best Practices

BFF Pattern & SPA Security
Backend for Frontend, token storage in httpOnly cookies, Spring Cloud Gateway as BFF

The Problem with Tokens in the Browser

A Single Page Application (SPA) running in the browser has no secure, isolated storage. localStorage is readable by any JavaScript on the page — including injected scripts from XSS attacks. Even sessionStorage is accessible to JavaScript. An XSS vulnerability in a SPA that stores tokens in JS-accessible storage is a full token exfiltration.

The Backend for Frontend (BFF) Pattern

The BFF pattern moves the OAuth2 Client role to a server-side component that the SPA trusts. The flow:

SPA → GET /api/login → BFF (Spring Cloud Gateway)
BFF → redirects browser → Okta /authorize
Okta → code → BFF /callback
BFF exchanges code for tokens, stores tokens in server-side session
BFF → sets httpOnly, Secure, SameSite=Strict session cookie → Browser
SPA → calls /api/* with session cookie → BFF
BFF → retrieves token from session, forwards request → Resource Servers

The SPA never sees the access token. Tokens live only in server-side session storage (Redis). XSS in the SPA can't steal tokens — it can only make authenticated requests through the BFF, which can apply rate limiting, anomaly detection, and audit logging.

YAMLSpring Cloud Gateway as BFF (application.yml)
spring:
  cloud:
    gateway:
      routes:
        - id: orders-api
          uri: https://orders-api.internal
          predicates:
            - Path=/api/orders/**
          filters:
            - TokenRelay=    # Automatically relays OAuth2 access token
        - id: inventory-api
          uri: https://inventory.internal
          predicates:
            - Path=/api/inventory/**
          filters:
            - TokenRelay=

  security:
    oauth2:
      client:
        registration:
          okta:
            client-id: ${OKTA_CLIENT_ID}
            client-secret: ${OKTA_CLIENT_SECRET}
            scope: openid, profile, email, offline_access
        provider:
          okta:
            issuer-uri: https://dev-123.okta.com/oauth2/default

  session:
    store-type: redis       # Tokens stored in Redis, not browser
    timeout: 30m

# CSRF protection for the BFF (SPA sends XSRF-TOKEN cookie)
server:
  servlet:
    session:
      cookie:
        http-only: true
        secure: true
        same-site: Strict
✅

The BFF pattern is the current recommended approach for SPA security per the OAuth2 Security BCP (RFC 9700). It eliminates token exposure to JavaScript while providing a clean API surface. The SPA stays simple (no token management), and security concerns are centralized in the BFF.

SPA (React/Angular/Vue)

Use BFF pattern. Session cookie for BFF auth. Access token in memory only (never persisted). Refresh via BFF on page load. Never localStorage. Never send tokens to analytics/logging.

The In-Memory SPA Pattern (When BFF is Not an Option)

If you must handle tokens in the SPA without a BFF:

  1. Store access token in a JS module variable (in-memory, never persisted)
  2. Store refresh token in a Secure httpOnly cookie set by a minimal token endpoint on your own domain
  3. On page load / token expiry, silently refresh via a hidden iframe or service worker calling your token endpoint
  4. Implement a strict CSP (Content Security Policy) to mitigate XSS risk
  5. Set short access token TTL (5–15 minutes)
🔴

Content Security Policy is your XSS last line of defense. Even if a token is in memory, a relaxed CSP allows injected scripts to exfiltrate it via fetch() to an attacker domain. Set default-src 'self', restrict script-src, and use nonces or hashes for inline scripts. Test your CSP with the Content-Security-Policy-Report-Only header before enforcing.

DPoP, mTLS & Pushed Authorization Requests
Sender-constrained tokens, certificate binding, PAR — modern token security primitives

DPoP — Demonstrating Proof of Possession (RFC 9449)

Bearer tokens are dangerous because anyone who gets the token can use it. DPoP (Demonstrating Proof of Possession) binds the access token to a cryptographic key pair held by the client. Even if the token is stolen, it's useless without the private key that signed the DPoP proof.

How it works: The client generates an asymmetric key pair. When requesting a token, it includes a DPoP proof JWT — a short-lived JWT signed with its private key, containing the HTTP method and URL of the request. The AS binds the access token to the client's public key (stored in the cnf.jkt claim). For every API call, the client sends both the access token and a fresh DPoP proof. The RS verifies that the proof's signature matches the public key in the token's cnf claim.

HTTPDPoP — token request + API call
── Token Request with DPoP proof ────────────────────
POST /oauth2/v1/token
DPoP: eyJ0eXAiOiJkcG9wK2p3dCIsImFsZyI6IkVTMjU2IiwiandrIjp7Li4ufX0
     . (JWT signed by client's private key, contains htm+htu claims)

DPoP proof header:
{ "typ": "dpop+jwt", "alg": "ES256", "jwk": { client's public key } }

DPoP proof payload:
{
  "jti": "unique-id",    ← replay prevention
  "htm": "POST",         ← HTTP method
  "htu": "https://as.example.com/token",  ← URL
  "iat": 1718000000     ← must be recent (short-lived proof)
}

── Issued access token contains cnf (confirmation) claim ──
{
  "cnf": {
    "jkt": "JWK SHA-256 thumbprint of client's public key"
  }
}

── API call with DPoP-bound token ───────────────────
GET /api/orders HTTP/1.1
Authorization: DPoP <access_token>    ← "DPoP" not "Bearer"
DPoP: <new DPoP proof for this specific request>
# Each API call needs a fresh DPoP proof (htm + htu must match this request)

Mutual TLS (mTLS) Token Binding (RFC 8705)

mTLS uses TLS client certificates to bind tokens. The client presents a certificate during the TLS handshake to the AS. The AS stores a hash of the certificate's public key in the token's cnf.x5t#S256 claim. Resource servers verify that the TLS connection's client certificate matches the token's binding. Extremely strong — requires attackers to steal both the token AND the private key of the TLS certificate.

Used in: open banking (FAPI), enterprise service meshes (Istio mTLS), financial institutions. Operationally complex — requires PKI infrastructure, certificate lifecycle management, and mTLS-aware load balancers.

Pushed Authorization Requests — PAR (RFC 9126)

In standard Auth Code flow, the authorization request parameters travel in the URL — visible in browser history, server logs, and proxy logs. PAR pushes the request body directly to the AS (authenticated, server-to-server), receiving a request_uri that references the pre-registered parameters. The browser redirect only carries the opaque request_uri.

HTTPPAR flow (RFC 9126)
Step 1: Push auth params to AS (server-to-server, authenticated)
POST /oauth2/v1/par
Authorization: Basic base64(client_id:client_secret)

response_type=code
&client_id=my-app
&redirect_uri=https://app.example.com/callback
&scope=openid orders:read
&state=abc123
&code_challenge=E9Melhoa...
&code_challenge_method=S256

Response:
{
  "request_uri": "urn:ietf:params:oauth:request_uri:bwc4JDEhenoX0-7q4M70lg",
  "expires_in": 60
}

Step 2: Redirect browser with only the request_uri (short, opaque)
GET /oauth2/v1/authorize?
  client_id=my-app
  &request_uri=urn:ietf:params:oauth:request_uri:bwc4JDEhenoX0-7q4M70lg
# No sensitive parameters in the URL!
💡

PAR + PKCE + DPoP is the gold standard for high-security authorization flows. PAR prevents request tampering (parameters are AS-authenticated before the redirect), PKCE prevents code interception, and DPoP prevents token misuse even if stolen. This combination is required by FAPI 2.0.

What is FAPI?

FAPI (Financial-grade API) is a set of security profiles for OAuth2 and OIDC designed for high-risk, high-value API access — initially banking (Open Banking UK, PSD2), now extended to healthcare, government, and other regulated industries. FAPI defines stricter requirements on top of standard OAuth2.

CIBA — Client-Initiated Backchannel Authentication (RFC Implementer's Draft)

CIBA decouples authentication from the device requesting access. A service initiates an authentication request; the user approves on their phone (push notification via authenticator app). Used for: call center agents initiating actions on behalf of a user, IoT devices, decoupled front-end/back-end flows.

Service → POST /bc-authorize → AS (login_hint: user@example.com)
AS → push notification → User's Phone
User approves on authenticator app
Service → polls POST /token (auth_req_id) → AS
AS → { access_token, id_token }

Signed Request Objects (JAR — RFC 9101)

JWT-Secured Authorization Requests (JAR) allow the client to package the entire authorization request as a signed JWT. This ensures the AS receives exactly what the client sent — no parameter tampering by a malicious redirect or proxy. Combined with PAR, the signed request is POSTed to the AS, providing both integrity and confidentiality.

💡

Most commercial OAuth2 providers (Okta, Auth0, Azure AD, Keycloak) support FAPI profiles or can be configured to enforce FAPI-level security. For regulated industries, explicitly verify FAPI 2.0 certification at the Open ID Foundation certification page before selecting an AS.

JWKS Key Rotation

Authorization Servers rotate their signing keys periodically (Okta rotates automatically every 90 days by default). The rotation process must be zero-downtime:

  1. AS generates new key pair, adds new public key to JWKS (both old and new keys present)
  2. AS starts signing new tokens with the new private key (new kid)
  3. Old tokens (signed with old key) are still valid until they expire
  4. Resource servers see an unknown kid, refresh their JWKS cache, find the new key
  5. After old token expiry window, AS removes the old key from JWKS

Spring Security's NimbusJwtDecoder handles this automatically — on unknown kid, it refreshes the JWKS and retries. Configure a sensible cache TTL and ensure your JWKS fetch has a timeout and retry with exponential backoff.

JavaCustom NimbusJwtDecoder with cache tuning
@Bean
public JwtDecoder jwtDecoder() {
    NimbusJwtDecoder decoder = NimbusJwtDecoder
        .withJwkSetUri("https://dev-123.okta.com/oauth2/default/v1/keys")
        .jwsAlgorithm(SignatureAlgorithm.RS256)
        .jwsAlgorithm(SignatureAlgorithm.ES256)
        .cache(Caffeine.newBuilder()
            .maximumSize(10)
            .expireAfterWrite(Duration.ofMinutes(10))
            .build())
        .restOperations(jwksRestTemplate())   // custom timeouts
        .build();

    // Custom validator chain
    List<OAuth2TokenValidator<Jwt>> validators = List.of(
        new JwtTimestampValidator(Duration.ofSeconds(10)),  // 10s clock skew
        new JwtIssuerValidator("https://dev-123.okta.com/oauth2/default"),
        new JwtClaimValidator<>("aud",
            aud -> ((List<?>) aud).contains("https://api.example.com"))
    );
    decoder.setJwtValidator(new DelegatingOAuth2TokenValidator<>(validators));
    return decoder;
}

private RestOperations jwksRestTemplate() {
    SimpleClientHttpRequestFactory factory = new SimpleClientHttpRequestFactory();
    factory.setConnectTimeout(2000);
    factory.setReadTimeout(5000);
    return new RestTemplate(factory);
}

Incident Response — Token Compromise Playbook

  1. Revoke immediately: Call POST /oauth2/v1/revoke with the compromised token. If refresh token family, revoke all tokens in the family.
  2. Force re-authentication: Terminate all sessions for the affected user/service account via Okta Admin API.
  3. Rotate secrets: If client_secret was compromised, generate a new one in Okta immediately. Update all deployments.
  4. Analyze blast radius: Query Okta System Log for all API calls made with the compromised token. What data was accessed?
  5. Key rotation: If signing key was compromised (unlikely for hosted AS), coordinate emergency key rotation with the AS operator.
  6. Post-mortem: How was the token leaked? Log pipeline? Referrer header? Browser storage? XSS? Fix the root cause, not just the symptom.
